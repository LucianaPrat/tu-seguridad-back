## Bugs

### 1. Magic-link and password-reset emails link to pages the web does not have — confirmed

`src/modules/auth/smtp-credential-delivery.service.ts:21-30` builds:

| Purpose | Backend link path | Web route (`tu-seguridad-front/src/App.tsx:115-119`) |
|---|---|---|
| invitation | `/invitations/accept` | `/invitations/accept` — matches |
| magic link | `/auth/magic` | `/auth/magic-link` — **mismatch** |
| password reset | `/auth/reset-password` | `/auth/change-password` — **mismatch** |

A user who clicks either link lands on a route the web does not define. Fix on whichever side owns
the URL; the two must agree.

### 2. Realtime alerts reach nobody — confirmed

The backend emits `alert-event` on the socket.io namespace `/events`, to room `space:<spaceId>`
(`src/modules/events/events.gateway.ts:18,102`, fired from `alert-events.service.ts:91`). The web has
no `socket.io-client` dependency and no `io(` call; only a comment mentions it
(`src/lib/queryClient.ts:5`). The event list refreshes only when react-query refetches
`GET /events` (`staleTime` 30 s, no refetch on focus, no `refetchInterval`).

### 3. Possible port clash: OTel collector vs MediaMTX on 8888 — not verified

`ops/otel-collector/config/collector.prod.yaml` serves the collector's own metrics on
`127.0.0.1:8888`. `docker-compose.yml` publishes MediaMTX HLS on host `8888`. If both run on the
same host, one of them likely fails to bind. Check with both up before the next deploy.

## Gaps (not bugs, but known holes)

- **Metrics never reach Grafana.** The collector pipeline is `traces` only. The backend exposes
  `GET /metrics` (incl. `dvr_event_streams_active`, `dvr_event_stream_drops_total`,
  `dvr_event_motion_total`), but nothing scrapes it.
- **Nobody is alerted when a recorder drops.** The listener already notices within
  `DVR_EVENTS_IDLE_SECONDS` (heartbeat ~9.5 s, default 30 s). Before #105 that was only a warn log.
  #105 exposes it; alerting is still to do (below).
- **WhatsApp channel has no sender.** `AlertChannel.whatsapp` exists in the schema and in the
  default routings (disabled), but `alert-events.service.ts:218` says `call` and `whatsapp` have no
  sender yet. Only email delivers.
- **`docs/architecture-diagram.html` is stale** (hand-drawn SVG, last touched 2026-09-10). #103
  replaces it with Mermaid; delete it once #103 merges.
- **35 high/moderate npm advisories** remain in production deps (axios, joi, qs, @grpc/grpc-js,
  nodemailer, …). CI gates on `critical` only, so they do not fail a build. `npm audit --omit=dev`.

## Decisions and recommendations taken in the session

### Monitoring the recorder connection

- **Where:** detection inside NestJS (it is the only thing on the LAN with the recorder and it
  already knows); alerting **outside** it, in Grafana Cloud, because a dead process cannot report
  its own death. GitHub Actions rejected: runs in GitHub's cloud and cannot reach the recorder.
- **Step 3 — done in #105.** Per-space status in the listener; public counts on
  `/health/dependencies`; full detail behind auth on `GET /api/v1/dvr/events`. Per-space times are
  kept off the public route on purpose: `lastMotionAt` tells when someone moved in front of a camera.
- **Step 1 — to do.** Add a `prometheus` receiver to the collector scraping the backend's
  `/metrics`, and a `metrics` pipeline to the existing `otlphttp/grafana` exporter.
- **Step 2 — to do.** Grafana Cloud alert rules:
  - `dvr_event_streams_active == 0` for 5 min: backend alive, recorder unreachable.
  - absence of any backend metric for 5 min: backend or host down.
  - Contact point: email is native. WhatsApp is not — needs a webhook to Twilio/Meta. Telegram is
    native if that is acceptable.
- **"No events for an hour":** no heartbeat = dead connection, caught in ~30 s. Heartbeat but no
  motion is normal (night, empty place) and is not a fault signal. The real blind spot is a channel
  without motion linkage configured — checked by `POST /dvr/event-linkage`, not by a timer.
- **Owner-facing "your DVR is offline" notice** is a product feature, separate from ops alerting;
  it would go through alert routings and needs the WhatsApp sender first.

### Keeping the architecture diagram current

- Diagram as Mermaid in the repo (`docs/architecture.md`, copied into `README.md`), so it diffs in
  review. Not an Artifact: those live on claude.ai, outside the repo and CI.
- Auto-update on merge: recommended `anthropics/claude-code-action` on push to `develop` when
  controllers, gateways, `dvr`, `streaming` or `face-auth-client` change. **Not installed.** Needs
  `/install-github-app` and an `ANTHROPIC_API_KEY` repo secret (repo admin). Cheaper alternative:
  a CI check that fails a PR touching those paths without touching `docs/architecture.md`.
