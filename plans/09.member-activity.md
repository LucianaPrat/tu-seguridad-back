# 09 — Member Activity (logins and live-stream time)

> Implementation plan for the admin charts on `/members`: logins by weekday and month, and
> live-stream minutes by camera and by user. Audience: an AI coding agent implementing T01–T05 in
> order. A task is complete only when its Definition of Done (DoD) passes and the result is recorded
> in `09.member-activity.tasks.md`. Frontend counterpart: `tu-seguridad-front`
> `MemberActivityCharts`.

## 1. Context and fixed decisions

Before this plan only `users.last_login_at` existed (`UserAccessorService.recordLogin`), and the
MediaMTX hook `LiveStreamService.authorize` persisted nothing (`HitInterceptor` skips it on purpose).
There is no history to backfill: charts fill from the deploy onward.

- Admin only (`@Roles(SpaceMemberRole.admin)`); only current members of the caller space are counted.
- Window `days` in `7 | 30 | 90` (default 30) for weekday and streaming; monthly chart is a fixed
  last 12 months including the current one.
- "Day" and "month" are in the space DVR timezone, fallback `America/Montevideo`.
- Watch time granularity is one minute; a segment served from the browser cache does not count.

## 2. Model (migration `member_activity`)

- `LoginEvent` (`login_events`): `id`, `userId` (FK users, cascade), `method` enum
  `LoginMethod = password | magic_link | face`, `createdAt`. Indexes `(userId, createdAt)`, `createdAt`.
- `StreamWatchMinute` (`stream_watch_minutes`): `spaceId`, `userId`, `cameraId`, `minute`;
  `@@id([spaceId, userId, cameraId, minute])`, `@@index([spaceId, minute])`. No FKs: an append-only log
  swept by retention.

## 3. Behaviour

- `recordLogin(id, method)` updates `lastLoginAt` and inserts the event in one `$transaction`.
  Callers pass `password` (auth), `magic_link` (credential recovery), `face` (face identity).
- `authorize` calls `recordWatch(spaceId, sub, request.path)` after `canSeeCamera` and before the
  memo (the memo is per space+path, not per viewer). Fire-and-forget; a failure is logged and never
  changes the hook's answer. In-memory dedupe per `space|user|camera` for the current minute, plus
  `createMany({ skipDuplicates })` for multi-instance.
- Retention sweeps both tables at `RETENTION_ACTIVITY_DAYS` (default 400, batch-limited `DELETE ... LIMIT`).
- `GET /members/activity?days=` declared before any `:param` GET. Response:
  `{ timezone, loginsByWeekday: [{userId, weekday 0=Sunday..6, count}], loginsByMonth: [{userId, month 'YYYY-MM', count}],
  watchByCamera: [{cameraId, minutes}], watchByUser: [{userId, minutes}] }`.
- Aggregation: login rows are bucketed in TypeScript with `Intl.DateTimeFormat` in the space zone
  (MySQL `CONVERT_TZ` needs the zone tables loaded); watch totals use Prisma `groupBy`.

## 4. Tasks

- **T01 — Schema and migration.** DoD: tables exist, `prisma generate` clean.
- **T02 — Login events.** DoD: three callers pass their method; accessor spec/caller specs assert it.
- **T03 — Watch minutes.** DoD: spec proves one write per minute, a new write on the next minute,
  no write for a non-member, and an admitted reader when the write fails.
- **T04 — Retention.** DoD: both sweeps run at the activity window; env validated and documented.
- **T05 — Endpoint.**  (superseded by v2 below.) DoD: admin-only metadata test, aggregation spec (timezone edge cases, window vs
  12 months, roster scoping), `openapi.json` regenerated.

## v2: accesses from hits

Weekday/month login counts are gone. Users often keep a saved token and never pass `/login`, so an
**access** is now a *session* derived from `hits` (one row per authenticated request, with `userId`,
never swept by retention, so history already exists). `login_events` is still recorded but no longer
exposed.

- Session: a run of a user's hits (`user_id` not null); a new one starts at the first hit or when the
  gap from the user's previous hit is **> 30 minutes** (exactly 30 is the same session). MySQL 8
  `LAG() OVER (PARTITION BY user_id ORDER BY created_at)` in `$queryRaw`
  (`MemberActivityAccessorService.findSessionStarts`); empty roster short-circuits to `[]`.
- Migration `20261125120000_hits_user_created_idx` adds `hits(user_id, created_at)`.
- Period = the last `days` (7|30|90, default 30) calendar days in the space timezone ending today
  inclusive; previous = the `days` days right before. Session starts are bucketed by local day in TS
  with `Intl` (zone from the DVR, fallback `America/Montevideo`).
- Response: `{ timezone, days[], accessesByDay[{date,userId,sessions}] (non-zero, period only),
  watchByDay[{date,cameraId,minutes}], watchByUserCamera[{userId,cameraId,minutes}],
  lastAccess[{userId,at ISO}] (all time, users with no hits omitted),
  previous{sessions,activeUsers,watchMinutes} }`. Removed: `loginsByWeekday`, `loginsByMonth`,
  `watchByCamera`, `watchByUser`.
- Tests: service spec (day boundary in Montevideo, previous totals, roster scoping, empty roster) and
  `member-activity.accessor.int-spec.ts` (30 vs 31 minute gap against real MySQL).
- Known edge: the first session of the previous period may be split by the fetch bound; negligible.
