# 06 — Event-Driven Capture: tu-seguridad-back

> Why the recorder is asked to speak instead of being polled, what was verified against the real
> DVR on 2026-09-09, and the decisions that follow. Audience: the repo owner (for the operational
> calls) and an AI coding agent or developer (for T01–T06).
> Each task has a **Definition of Done (DoD)**: exact commands and observable results. A task is
> complete only when every DoD item passes.

## 1. Context

The pipeline polls every camera on a 15/10/5 second ladder. Over a twelve-hour night, five wired
cameras cost roughly **14 400 ISAPI captures and 14 400 detection POSTs upstream** — to catch
something that happens a handful of times.

The recorder already knows. It runs its own detector on continuous video and will report over a
connection it holds open. Two payoffs, and the second is the larger:

1. **Cost** — capture on motion instead of on a clock.
2. **Recall.** A person crosses a street camera in three to eight seconds. A fifteen-second grid can
   miss them outright, which is a different failure from the confidence-threshold tuning
   [`plans/05`](05.detection-quality.md) chased, and not one a threshold can fix. Event-triggered
   capture fires about a second into the movement, with the subject mid-frame.

### What was measured

Hikvision DVR-208G-M1, firmware V4.71.410, at `192.168.1.250`, over HTTP digest.

| Question                                                 | Answer               | Evidence                                                                                                                                               |
| -------------------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Does `alertStream` work over the existing digest client? | Yes                  | `GET /ISAPI/Event/notification/alertStream` returns `multipart/mixed`, boundary `--boundary`, one `<EventNotificationAlert>` per part                  |
| Does it publish motion out of the box?                   | **No**               | Before the change the stream carried heartbeats only. All eight `VMD-N` triggers carried `whiteLightOut-N` and `record-N` and no `center` notification |
| What makes it publish?                                   | The `center` linkage | Adding it by hand produced `eventType=VMD`, `eventState=active` on channels 4, 7 and 8 within seconds                                                  |
| Is there an idle signal?                                 | Yes, ~9.5 s          | `videoloss` / `inactive` / `channelID 0`, and it **pauses during a motion burst**                                                                      |
| Does the recorder say motion ended?                      | **Never**            | No `inactive` for VMD ever arrives. Every notification is a bare pulse — edge detection is impossible                                                  |
| Does it repeat?                                          | Yes                  | One walk past produced 4 consecutive pulses on channel 4 and 5 on channel 8, interleaved with channel 7                                                |
| Is this pixel differencing?                              | No                   | `<targetType>human,vehicle</targetType>` — the recorder classifies at the edge                                                                         |
| Can we ask what the firmware supports?                   | No                   | `GET /ISAPI/Event/triggers/VMD-1/capabilities` answers `statusCode 4` / `Invalid Operation` / `notSupport`                                             |
| Is a write safe to compose?                              | **No**               | A `PUT` to `/notifications` replaces the whole list. A composed document silently deletes record-on-motion and light-on-motion                         |
| Is `statusCode 1` proof?                                 | No                   | The firmware answers `OK` to writes whose elements it dropped. Only a re-`GET` proves anything                                                         |
| How many channels are wired?                             | 5 of 8               | 3, 4, 5, 7, 8 online; 1, 2 and 6 read `NO VIDEO`. The first walk test failed because channel 1 is an empty socket                                      |

Two findings that came from running axios, not from reading it:

- **`maxContentLength` is fatal on a long-lived stream.** On axios 1.18.1, `maxContentLength: 1000`
  killed a stream at 894 bytes with `maxContentLength size of 1000 exceeded`; omitted and `Infinity`
  both streamed indefinitely.
- **An axios `timeout` is disarmed once the response headers land**, so it does not protect a stream
  that later goes quiet.

### Two decisions that must not be silently reverted

**This reverses [`plans/05`](05.detection-quality.md) §7, "No motion-detection fallback."** That
refusal was about pixel differencing on eight channels crying wolf. It does not apply here: the
recorder classifies human and vehicle at the edge, and the trigger raises no alerts — it asks the
existing pipeline for a frame and the pipeline decides.

**The poll is retuned, not removed.** A push transport has no acknowledgement, no replay, and a
socket that dies without saying so; a recorder rebooting at 03:00 stops publishing and reports
nothing. The passive rung becomes a five-minute watchdog, which bounds that failure per camera.

## 2. Tasks

### T01 — Sign the recorder request with its own verb

The digest HA2 is `METHOD:uri` and the client hardcoded `GET`. A write signed as a read is refused,
and refused as a `401` — which the client reads as a stale nonce and reports as a rejected
credential, sending the operator to re-type a password that was fine. Also: two paths abandon a
`401` response, which is free for a buffered body and leaks a socket for a streamed one.

**DoD** — `buildAuthorization` takes the method; `get()` becomes `request()`; a `discard` helper
destroys a `Readable` body on both abandon paths. A unit test asserts the digest `response` field
for a PUT is built from `md5('PUT:/ISAPI/Event/triggers/VMD-4/notifications')`. All pre-existing
tests still pass.

### T02 — `linkMotionEvents` on the port

**DoD** — `DvrClientPort.linkMotionEvents(connection, externalId)` returning
`Either<'linked' | 'alreadyLinked'>`. The ISAPI implementation reads the trigger's notification list,
returns `alreadyLinked` without writing when `center` is already present, splices the block before
the last closing tag (refusing, with no PUT, when that tag is absent), writes, and re-reads to
confirm. `FakeDvrClientService` grows the method. Six unit tests, including one asserting **no PUT**
is issued for a body that is not a notification list.

### T03 — `POST /api/v1/dvr/event-linkage`

Admin only, and a route of its own rather than a step inside `PUT /dvr`: it writes configuration into
security hardware, and a write that happens as a side effect of saving a password is a write nobody
chose.

**DoD** — serial walk over the recorder's own roster, best effort with a per-channel report, stopping
on the first `UPSTREAM_TIMEOUT` and marking the rest not attempted; `UPSTREAM_ERROR` only when every
channel failed; no `lastTestAt`/`lastTestOk` written. `openapi.json` regenerated with `outcome` as an
explicit enum. Controller description states that the route **does not enable motion detection**.

### T04 — `DvrEventListener`

**DoD** — one long-lived connection per recorder, per-camera debounce, idle watchdog armed before the
connect and fed by every notification, reconnect with backoff, credential-fingerprint reconciliation
once a minute, clean abort on `onModuleDestroy`. Motion enters the pipeline through the existing
`PollingScheduler.pollGuarded`. `forget` added to the delete fan-out in `cameras.service.ts` and its
doc comment updated from five holders to six. Three metrics registered. Eighteen unit tests, and the
suite exits with no open handles.

### T05 — Configuration

**DoD** — `DVR_EVENTS_ENABLED` (default `false`), `DVR_EVENTS_DEBOUNCE_SECONDS` (`5`, floor `1`) and
`DVR_EVENTS_IDLE_SECONDS` (`30`, floor `5`). `POLLING_PASSIVE_SECONDS` becomes a conditional default —
`15` with events off, `300` with them on — so a deployment that upgrades without turning events on is
not silently made twenty times less responsive. Two schema-spec assertions cover the branch.
`DVR_EVENTS_ENABLED=false` forced in both test setup files.

### T06 — Documentation

**DoD** — README stack row, detection-pipeline sentence, cadence table and a `Recorder-pushed events`
section; the roadmap bullet rewritten in place to "Decided: both"; an `ARCHITECTURE.md` bullet on why
the poll survives; a `docs/BEST_PRACTICES.md` operator runbook; this plan and its tracker.

## 3. Verified end to end

Against the real recorder, through the compiled adapter rather than curl:

```
discoverChannels ok=true  1:offline 2:offline 3:online 4:online 5:online 6:offline 7:online 8:online
linkMotionEvents(4) -> alreadyLinked      # idempotent, no write issued
linkMotionEvents(99x) -> refused VALIDATION_ERROR
openEventStream ok — heartbeats classified as keepalive at ~9.5s
```

And the dangerous branch, exercised by stripping `center` from channel 2 and putting it back:

```
after strip -> center present? false
linkMotionEvents(2) -> linked
center restored?      true
record-2 survived?    true       # the regression a composed document would have caused
whiteLightOut-2 ok?   true
second call idempotent? alreadyLinked
```

That run also proves the T01 digest fix on real hardware: without it the PUT would have come back as
a credential rejection.
