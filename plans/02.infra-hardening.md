# 02 — Infra Hardening: tu-seguridad-back

> Implementation plan to close the highest-leverage infra/ops gaps found in a state-of-the-art audit of the repo.
> Audience: an AI coding agent (or developer) implementing tasks T01–T08 in order.
> Each task has a **Definition of Done (DoD)**: exact commands and observable results. A task is complete only when every DoD item passes.

## 1. Context

Plan `01.setup.md` shipped a solid foundation (NestJS 11, layered architecture, `Either` errors, Prisma accessors, JWT auth, Pino, opt-in OTel, Throttler, Terminus health, PM2). An infra/architecture audit (not user-feature-focused) found this repo runs **single-instance** (PM2 fork mode), has **no CD** (CI only tests), **no runtime observability beyond logs**, **no dependency scanning**, and **plain `.env` secrets** — acceptable for the current 8-camera/home-security scale, but each of those is a real gap against 2026 backend best practices.

The full audit produced 10 candidate items. The repo owner decided:
- **Skip #1 (Docker containerization)** — not wanted for this project.
- **Skip #3 (Redis: distributed throttler / cache / socket.io adapter) and #4 (BullMQ queue for the polling pipeline)** — both need a Redis instance; not affordable on AWS at this project's current cost budget. Revisit if the project ever needs multi-instance scaling or the cost picture changes.

This plan covers the remaining **7 items (#2, #5, #6, #7, #8, #9, #10 from the audit)**, re-scoped to work without containers or Redis. Numbered `02` as the next plan in sequence — this supersedes the informal "02 — Automatic polling hardening" line in `README.md`'s Roadmap where it overlaps (the resilience piece, T03 below); DVR-snapshot-specific reliability work (FPS tuning, reconnection metrics) that isn't infra-generic stays out of scope here, left for whoever picks that up.

None of this changes API surface, DTOs, or user-visible behavior — it is entirely ops/infra.

## 2. Stack additions

| Concern | Choice | Why not something else |
|---|---|---|
| CD | GitHub Actions + SSH deploy to the existing PM2 host | No containers, no orchestrator — matches how prod already runs (`ecosystem.config.js`) |
| Circuit breaker | `opossum` | De-facto standard Node circuit breaker, zero infra dependency (in-memory) |
| Metrics | `@willsoto/nestjs-prometheus` + `prom-client`, `/metrics` endpoint | Pull-based, no extra service to run; pair with any existing/future Prometheus scraper |
| Error tracking | `@sentry/node` (or `@sentry/nestjs` if current at implementation time) | Free tier covers this project's volume; opt-in via `SENTRY_DSN`, same pattern as `OTEL_ENABLED` |
| Secrets at rest | `sops` + `age` | Free, git-native, no recurring SaaS cost (ruled out AWS Secrets Manager/Vault for the same cost reason as Redis) |
| Field encryption | Node built-in `crypto` (AES-256-GCM) | No new dependency; lives entirely inside the accessor layer |
| Dependency scanning | `npm audit` (CI gate) + Dependabot | Both free, built into GitHub |
| Contract artifact | Swagger's existing `DocumentBuilder`, exported to a committed `openapi.json` | Reuses `src/cross/config/swagger.config.ts`, no new library |

Install latest minor within reason. Pin nothing beyond what's already pinned.

## 3. Conventions (apply to every task, in addition to `AGENTS.md` and `.standards/`)

- Every new env var: add to `EnvNames` (`src/cross/common/constants.ts`) **and** the Joi schema (`src/cross/config/env-validation.schema.ts`) in the same commit, with a dev default where safe and `required()` in production otherwise (mirror the existing `stringRequiredInProduction` pattern) — and to `.env.example`/`README.md`'s env table.
- Every new optional integration (Sentry, metrics auth token) must **no-op cleanly when unset** — same posture as `OTEL_ENABLED`. Never make local dev depend on a new external service.
- No `Either`/DTO/API-surface changes in this plan. If a task seems to need one, stop and flag it instead of improvising.
- One Conventional Commit per task, English only, no AI-agent trace (see `.standards/standards/GIT.md`).

## 4. Tasks

### T01 — Dependency & supply-chain scanning in CI

**Goal:** catch vulnerable dependencies before merge, for free.

**Steps:**
1. Add `.github/dependabot.yml`: `package-ecosystem: npm`, directory `/`, weekly schedule, target branch `develop` (not `main` — matches this repo's branch model), grouped minor/patch updates.
2. `.github/workflows/pr-tests.yml`: add a step right after `npm ci` — `run: npm audit --audit-level=high`.

**DoD:**
- [ ] `.github/dependabot.yml` parses (`python3 -c "import yaml;yaml.safe_load(open('.github/dependabot.yml'))"`).
- [ ] `npm audit --audit-level=high` currently exits 0 locally (document any accepted exception if not).
- [ ] Temporarily lower `--audit-level` to `low` to confirm the step actually fails the job on a real finding, then revert to `high`.
- [ ] Commit `ci: add dependency audit gate and dependabot config`.

### T02 — CD pipeline (SSH + PM2, no containers)

**Goal:** an actual deploy path exists; today CI only tests.

**Steps:**
1. New `.github/workflows/deploy.yml`: trigger on push to `main` (production is promoted there per the branch model) or `workflow_dispatch` for manual runs.
2. Job steps: checkout → SSH into the prod host (`appleboy/ssh-action` or a plain `ssh`/`rsync` step) using repo secrets `PROD_HOST`, `PROD_SSH_USER`, `PROD_SSH_KEY` → on the host: `git fetch && git checkout <sha>`, `npm ci --omit=dev`, `npm run build`, `npx prisma migrate deploy`, `pm2 reload ecosystem.config.js --env production --update-env`.
3. Post-deploy health gate: curl `/health/ready` with a few retries (short backoff); fail the job if it never returns 200. Document (in the workflow's own comments) that `pm2 reload` in fork mode with `instances: 1` is a fast restart, not a zero-downtime swap — acceptable at current scale, revisit if that ever matters.
4. Document rollback: keep the previous deployed git SHA noted in the workflow's job summary; rollback = re-run the workflow pointed at that SHA (`workflow_dispatch` input), no automated rollback logic needed at this scale.

**DoD:**
- [ ] YAML parses.
- [ ] Manual dry run against the real prod host (needs the repo owner's SSH access — flag this as a manual verification step if it can't be exercised from this environment).
- [ ] A deliberate bad deploy (e.g. a failing migration) leaves the job red without leaving the host mid-upgrade (verify `pm2 ls` still shows the previous build running).
- [ ] Commit `ci: add deploy pipeline via ssh and pm2 reload`.

### T03 — Circuit breaker for the face-auth client

**Goal:** stop hammering an already-degraded, IP-throttled upstream with full-timeout requests.

**Steps:**
1. `npm i opossum && npm i -D @types/opossum`.
2. In `src/modules/face-auth-client/face-auth-client.service.ts`, wrap the existing HTTP call (the `firstValueFrom(this.httpService.post(...))` inside `detectPersons`) in an `opossum` `CircuitBreaker`, constructed once per service instance: `timeout` = `DETECT_TIMEOUT_MS`, `errorThresholdPercentage: 50`, `resetTimeout: 30000`, `rollingCountBuckets`/`rollingCountTimeout` defaults are fine.
3. On `open` circuit, short-circuit immediately to `buildError(ErrorCode.UPSTREAM_ERROR, 'face-auth circuit open')` — do not attempt the call. Log breaker `open`/`close`/`halfOpen` state transitions via `Logger`.
4. Expose current breaker state through `CameraStatusRegistry` (`src/modules/cameras/camera-status.registry.ts`) so it's visible on `GET /cameras/:id/status` — or, if that registry is per-camera and the breaker is global (one upstream), add a small module-level getter instead; decide based on `camera-status.registry.ts`'s actual shape and keep the simplest option that doesn't change the DTO shape without a reason.
5. Unit tests in `face-auth-client.service.spec.ts`: breaker opens after the configured failure threshold against a mocked failing `HttpService`; once open, subsequent calls resolve immediately without invoking `httpService.post`; after `resetTimeout`, a single probe call is attempted (half-open).

**DoD:**
- [ ] `npm test -- face-auth` green, including the new breaker tests.
- [ ] Manual: point `FACE_AUTH_API_URL` at an unreachable host locally, trigger several `analyze` calls — after the threshold, latency drops to near-zero (fails fast) instead of waiting the full `DETECT_TIMEOUT_MS` each time.
- [ ] Commit `feat: circuit breaker around face-auth upstream calls`.

### T04 — Prometheus metrics

**Goal:** basic RED metrics (rate, errors, duration) — today there is zero metrics endpoint, only opt-in traces.

**Steps:**
1. `npm i @willsoto/nestjs-prometheus prom-client`.
2. `PrometheusModule.register()` in `app.module.ts`; the `/metrics` route it creates is unprefixed by default — exclude it from JWT auth (`@Public()` equivalent on its controller, or `setGlobalPrefix`'s `exclude` list alongside `docs`/`health`) but **do not** expose it unauthenticated to the public internet: gate it behind a static shared-secret header check (new `EnvNames.METRICS_TOKEN`, compared in a small guard) since there's no reverse proxy/firewall layer (Docker/nginx declined) to restrict it at the network level instead.
3. New metrics, recorded at the points that already exist:
   - `http_request_duration_seconds` (histogram, labels `method`/`route`/`status`) — record in a new interceptor alongside `EitherInterceptor`/`HitInterceptor` (`src/cross/interceptors/`), or extend `HitInterceptor` since it already observes every request's `finish` event.
   - `throttler_rejections_total` (counter) — increment wherever the 429 currently gets thrown; check `src/cross/config/throttler.options.ts` for the cleanest hook (custom `throwThrottlingException` override if the version in use supports it).
   - `websocket_connections_active` (gauge) — increment in `EventsGateway.handleConnection`, decrement on disconnect (add an `OnGatewayDisconnect` handler — not currently implemented).
   - `pipeline_poll_total{status="success"|"error"}` and `pipeline_poll_duration_seconds` — record inside `PollingScheduler.pollOnce` (`src/modules/pipeline/polling.scheduler.ts`), using data already computed there (`snapshot.ok`, latency).
4. Unit tests for each new recording point (mock the metric provider, assert `.inc()`/`.observe()` called with expected labels).

**DoD:**
- [ ] `curl -H "X-Metrics-Token: <token>" /metrics` (adjust header name to whatever's implemented) returns Prometheus text format with default Node process metrics plus the four custom ones.
- [ ] A few manual requests move `http_request_duration_seconds`'s count; a forced 429 moves `throttler_rejections_total`; a WS connect/disconnect moves the gauge up then down.
- [ ] `npm test` green with new unit tests.
- [ ] Commit `feat: prometheus metrics endpoint with request, throttler, ws and pipeline metrics`.

### T05 — Error tracking (Sentry)

**Goal:** unexpected 500s get surfaced somewhere a human will see them, not just buried in logs.

**Steps:**
1. `npm i @sentry/node` (confirm the current recommended NestJS integration package name at implementation time — the ecosystem has moved between `@sentry/node` manual wiring and a dedicated `@sentry/nestjs` package).
2. New `EnvNames.SENTRY_DSN` (Joi: optional string, no dev default — absence means disabled). Init `Sentry.init({ dsn })` in `main.ts`, gated by the env var being set, **before** `NestFactory.create` — same ordering constraint already documented for `observability/tracing.ts`.
3. Hook into `src/cross/interceptors/either.interceptor.ts`'s `catchError` branch: call `Sentry.captureException(error)` only on the **unexpected**-error path (the one that produces a 500 envelope today) — never for `Either` failures (`ok:false`) or already-mapped `HttpException`s, to avoid noise from routine 400/401/404s.
4. Add a `beforeSend` scrub matching the existing Pino redaction: strip any `snapshotUrl` value and the `Fa-Token`/`Authorization` headers from breadcrumbs/context before they leave the process.
5. Unit test on the interceptor: `Sentry.captureException` (mocked) called exactly once for an unmapped thrown error, never called for an `Either` `ok:false` result or a thrown `HttpException`.

**DoD:**
- [ ] `npm test -- either` green with the new assertions.
- [ ] `SENTRY_DSN` unset → app boots and runs with zero Sentry network activity (confirm no outbound calls, e.g. via a network monitor or simply the absence of any Sentry log line).
- [ ] Manual (needs a real or test Sentry project): set `SENTRY_DSN`, hit a route forced to throw an unmapped error, confirm it appears in the Sentry dashboard within seconds, with `snapshotUrl`/tokens absent from the payload.
- [ ] Commit `feat: sentry error tracking on unexpected failures`.

### T06 — Secrets management + `snapshotUrl` encryption at rest

**Goal:** production secrets stop living as plaintext on the host filesystem; the one genuinely sensitive DB column (`Camera.snapshotUrl`, may embed DVR basic-auth) stops being plaintext in the database too.

**Steps — secrets (a):**
1. Adopt `sops` + `age` (both free CLI tools, no running service): generate an `age` keypair, keep the private key only on the prod host (`~/.config/sops/age/keys.txt`) and as a GitHub Actions secret (`SOPS_AGE_KEY`) for the deploy pipeline from T02.
2. Encrypt a `secrets.enc.yaml` (or per-env `secrets.<env>.enc.yaml`) containing the real production values for `JWT_SECRET`, `JWT_REFRESH_SECRET`, `DATABASE_URL`, `FACE_AUTH_TOKEN`, etc. — commit the **encrypted** file, never the plaintext.
3. T02's deploy workflow decrypts it to `.env` on the host (`sops -d secrets.enc.yaml > .env`) as a step before `pm2 reload`. Document the key-rotation procedure (re-encrypt with a new recipient, remove the old `age` key) in `docs/BEST_PRACTICES.md`.

**Steps — snapshotUrl encryption (b):**
4. New `EnvNames.SNAPSHOT_URL_ENCRYPTION_KEY` (Joi: required in production, 32-byte base64/hex, fail-fast like `JWT_SECRET`).
5. In `src/data/accessors/camera.accessor.ts`: encrypt `data.snapshotUrl` (AES-256-GCM via Node's `crypto`, random IV per value, store `iv:authTag:ciphertext` as the stored string) inside `create`/`update` before calling `this.prisma.camera.create/update`; decrypt `snapshotUrl` on the way out of `findAll`/`findById`. This stays entirely inside the accessor — no change needed in `CamerasService`, the mapper, or DTOs, since they already only see plaintext in and out.
6. One-off data migration script (`scripts/encrypt-existing-snapshot-urls.ts`, run manually once against prod, not part of CI): reads every `Camera` row directly via `PrismaService`, encrypts the existing plaintext `snapshotUrl`, writes it back.
7. Integration test in `camera.accessor.int-spec.ts`: create with a plaintext URL via the accessor, then assert a raw `prisma.$queryRaw`/direct client read of the row shows ciphertext, and that `findById` returns the original plaintext (round-trip).

**DoD:**
- [ ] `npm run test:int` green including the new round-trip assertion.
- [ ] Missing/malformed `SNAPSHOT_URL_ENCRYPTION_KEY` in production fails fast at boot with a Joi message (mirrors `JWT_SECRET`'s existing behavior).
- [ ] Manual: after running the one-off migration script against a copy of the data, `SELECT snapshotUrl FROM cameras` (or Prisma Studio) on the raw DB shows ciphertext, not a readable URL.
- [ ] `sops -d secrets.enc.yaml` decrypts correctly locally with the dev `age` key; `git grep` confirms no plaintext secret ever committed.
- [ ] Commit `feat: field-level encryption for camera snapshotUrl` (accessor change) and a separate `chore: adopt sops+age for production secrets` (deploy/docs change) — two commits, two concerns.

### T07 — Deeper health checks + graceful shutdown

**Goal:** `/health/ready` today only pings the DB; shutdown today only disconnects Prisma, dropping in-flight WS clients and leaving the polling scheduler mid-tick.

**Steps:**
1. `src/modules/health/health.controller.ts`: add a second Terminus indicator (new `FaceAuthHealthIndicator`, mirroring `PrismaHealthIndicator`'s shape) doing a cheap, short-timeout reachability check against `FACE_AUTH_API_URL`. Do **not** fold it into `/health/ready`'s existing check array if that would make the whole app report not-ready just because the upstream is degraded (this app can still serve camera/zone CRUD without it) — add it as a separate `GET /health/dependencies` endpoint instead, `@Public()`, version-neutral like the existing health routes.
2. `src/main.ts`: extend the `SIGINT`/`SIGTERM` shutdown sequence (currently just `PrismaService.onModuleDestroy` disconnecting) to, in order: stop `PollingScheduler` from starting new poll ticks (it already has `onModuleDestroy` clearing its sync timer — verify in-flight polls are allowed to finish, not killed), close the Socket.IO server so connected WS clients get a clean `disconnect` event rather than a dropped connection, then let Nest's own `enableShutdownHooks()` (already present) run the rest of the module teardown (Prisma disconnect included).
3. Test: an e2e/int-spec (or a targeted unit test around the shutdown sequence) asserting a connected `socket.io-client` receives a `disconnect` event when the server calls its shutdown path, and that `PollingScheduler`'s sync timer is confirmed cleared (already partially covered — extend rather than duplicate).

**DoD:**
- [ ] `curl /health/dependencies` reflects a real up/down face-auth reachability check (verify both states — point `FACE_AUTH_API_URL` at something unreachable to see the down case).
- [ ] `/health/ready` is unaffected by face-auth being down (still DB-only, as today).
- [ ] Manual: `kill -SIGTERM <pid>` on a locally running instance with a connected WS client — client receives a clean disconnect event (not a raw connection reset); log shows the polling scheduler stopped before Prisma disconnects.
- [ ] Commit `feat: face-auth reachability check and graceful ws/scheduler shutdown`.

### T08 — OpenAPI contract export in CI

**Goal:** the API contract becomes a diffable artifact instead of only a live `/docs-json` — useful for the frontend team and for catching accidental breaking changes.

**Steps:**
1. Small script (`scripts/export-openapi.ts`, `ts-node`-run): boots just enough of the app (reuse `AppModule` + the same `setupSwagger`/`DocumentBuilder` config from `src/cross/config/swagger.config.ts`, but skip `app.listen()`) to call `SwaggerModule.createDocument(...)` and write the result to `openapi.json` at the repo root.
2. Add an npm script: `"openapi:export": "ts-node scripts/export-openapi.ts"`.
3. CI step in `pr-tests.yml` (after build): regenerate `openapi.json` into a temp path and `diff` it against the committed one; fail the job with a clear message ("run `npm run openapi:export` and commit the result") if they differ — do not auto-commit, to keep history clean and intentional.
4. Commit the initial `openapi.json` generated from the current API surface.

**DoD:**
- [ ] `npm run openapi:export` produces a valid JSON file; `python3 -m json.tool openapi.json > /dev/null` succeeds.
- [ ] Deliberately add a throwaway DTO field, confirm the CI diff step fails; regenerate and confirm it passes; revert the throwaway change.
- [ ] Commit `ci: export and diff-check openapi contract`.

## 6. Out of scope (deferred, with reason)

- **Docker containerization** — declined by the repo owner for this project.
- **Redis** (distributed throttler storage, cache layer, socket.io Redis adapter) — cost-prohibitive on AWS at current scale. Revisit if multi-instance scaling is ever needed.
- **BullMQ / queue-based pipeline** — same Redis dependency as above; the in-process `PollingScheduler` stays as-is.
- **DVR-snapshot-specific reliability** (per-camera FPS tuning, reconnection metrics) — narrower than this plan's infra scope; still open, tracked informally in `README.md`'s Roadmap.
