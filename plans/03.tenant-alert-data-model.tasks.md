## Migration safety (T01)

- Confirmed by product owner: no production data must be retained.
- Development and test databases are treated as disposable for this migration.
- The migration destructively replaces `cameras`, `zones`, `zone_events` and `users`; the upgrade
  rehearsal in T08 is still mandatory before release.
- `users` joined that list during review. Altering it in place added `first_name`, `last_name` and
  `phone` as `NOT NULL` with no default, which backfills `''` into every existing row — a silently
  profile-incomplete account that the T04 login gate would still accept. `hits` is technical
  telemetry, has no foreign key to `users`, and is left untouched.

## Migration constraint review (T02)

- `space_members.user_id` is unique and `(space_id,user_id)` is unique.
- `dvrs.space_id` is unique; `cameras(dvr_id,external_id)` is unique.
- `monitor_zones_rectangle_bounds_check` rejects negative coordinates, non-positive dimensions and
  rectangles extending beyond 100 percent.
- `alert_events` foreign keys use `SET NULL` for camera, zone and snapshot historical references;
  ownership and membership relations use `RESTRICT`.
- `snapshots.data` is `MEDIUMBLOB`; no schema field stores a DVR-derived snapshot URL.
- `spaces.owner_user_id` is unique, so `User.ownedSpace` is a one-to-one relation, not a list.
- `cameras` carries one composite `(dvr_id, deleted_at)` index: every tenant-scoped read filters
  both columns together.
- `event_deliveries.error` is `TEXT`. At `VARCHAR(191)` a long provider error aborted the write
  that records the failure, leaving the row on its previous status.
- `dvrs.password_encrypted` is `VARCHAR(512)`, leaving room for a key-version prefix on the
  encryption envelope.

## Migration rehearsal evidence (T02)

The first revision altered `cameras` and `users` in place. Applied to a schema at
`20260720061441_init` holding two camera rows, one zone row and one user row, it aborted:

```
ERROR 1062 (23000) at line 234: Duplicate entry '' for key 'cameras.cameras_dvr_id_external_id_key'
```

MySQL DDL is not transactional, so that left a half-applied schema: new tables created, `zones` and
`zone_events` already dropped, no foreign keys added, and no down migration to retreat to. The
rewritten migration drops those four tables first and recreates them, and the same rehearsal now
completes with 14 tables, 22 foreign keys and the rectangle check constraint in place. Verified in
sync afterwards with `prisma migrate diff --from-migrations ... --exit-code` against both the
migration history and the development database.

## Seed behavior (T02)

- The whole seed runs in one `prisma.$transaction`. A user without its space and owner membership
  is exactly the state the T04 login gate rejects, and the seed is documented as idempotent.
- `ADMIN_EMAIL` is lowercased before the upsert; email uniqueness is global and compared
  case-insensitively.
- Routing defaults enable `email` for both alert types and leave `call`/`whatsapp` disabled: email
  is the one channel that needs no provider account, and T06 still has to pick the others. Rows are
  inserted with `skipDuplicates`, so re-seeding never stomps a matrix the operator has toggled.
- `ADMIN_PASSWORD` is now required in production with a 16-character minimum
  (`src/cross/config/env-validation.schema.ts`). The seeded admin is active, profile-complete, owns
  the space and holds the `admin` membership, so a production seed run with the variable unset would
  have published that account under the placeholder committed in `.env.example`.
