## Migration constraint review (T02)

- `space_members.user_id` is unique and `(space_id,user_id)` is unique.
- `dvrs.space_id` is unique; `cameras(dvr_id,external_id)` is unique.
- `monitor_zones_rectangle_bounds_check` rejects negative coordinates, non-positive dimensions and
  rectangles extending beyond 100 percent.
- `alert_events` foreign keys use `SET NULL` for camera, zone and snapshot historical references;
  ownership and membership relations use `RESTRICT`.
- `snapshots.data` is `MEDIUMBLOB`; no schema field stores a DVR-derived snapshot URL.
- `spaces.owner_user_id` is unique, so `User.ownedSpace` is a one-to-one relation, not a list.
- `cameras` carries one composite `(dvr_id, deleted_at)` index: every tenant-scoped read filters
  both columns together.
- `event_deliveries.error` is `TEXT`. At `VARCHAR(191)` a long provider error aborted the write
  that records the failure, leaving the row on its previous status.
- `dvrs.password_encrypted` is `VARCHAR(512)`, leaving room for a key-version prefix on the
  encryption envelope.

## Authentication decisions (T04)

- **Token claims.** The access token carries `spaceId`, membership `role` and `profileCompleted`
  next to `sub`/`email`, so no request derives its tenant from a resource id. A token missing
  `spaceId`/`role` is rejected by `JwtAuthGuard` rather than passed on: a pre-tenant token would
  otherwise reach an accessor with `undefined` as the space to scope by.
- **Deactivation lag is accepted and bounded.** `isActive` and membership are checked when a session
  is issued or refreshed, not on every request. Deactivating an account therefore takes effect at
  the next refresh — at most `JWT_EXPIRES_IN` (15 minutes). The alternative is a database read per
  request for a state that changes about once per employee.
- **Refresh tokens stay signed JWTs *and* become rows.** The standards require distinct secrets plus
  a `type` discriminator; the plan requires hash lookup, revocation and rotation. Both hold: the
  cookie value is a JWT, its hash is an `auth_tokens` row, and the row's `expires_at` is read back
  off the token's own `exp` so the two cannot drift.
- **Replay ends the family.** A refresh token whose signature verifies but has no usable row was
  already rotated, revoked or expired. That is either a stolen cookie or a client racing itself, and
  both are answered by revoking every refresh token the account holds. Rotation alone would let a
  thief keep racing the legitimate client.
- **Password reset is one transaction.** `AuthTokenAccessorService.consumePasswordReset` burns the
  token, writes the new hash and revokes every refresh token together. Split into three calls, a
  failure between them either loses the new password or leaves the sessions the reset was meant to
  end still valid.
- **Delivery is a port, not a provider.** `CredentialDeliveryPort` is what the domain depends on;
  `LoggedCredentialDeliveryService` is the placeholder until T06 picks a provider. Outside
  development it logs purpose and recipient only. In development it prints the raw token, because
  otherwise no local operator can accept an invitation or finish a reset, and the T07 smoke flow
  could not run at all. Production and test both take the redacted branch, so no shipped log and no
  fixture can carry a usable token — covered by a test.
- **Invited accounts start with placeholders.** Acceptance creates the user with empty name/phone and
  a hash of a discarded random secret, then hands out a `profileCompleted: false` session. Nothing
  can authenticate with that hash, and `ProfileCompletedGuard` blocks every route except `/auth/me`
  and `/auth/complete-profile` until the invitee sets its own values. This is the one place empty
  strings are reachable, and only while the flag is false — unlike the T01 `users` backfill, which
  would have produced the same shape on a *login-capable* account.
- **Password policy lives in one constant.** `AuthPolicy.MIN_PASSWORD_LENGTH` is 12, applied to
  registration, profile completion and password reset alike. A reset that accepted a weaker password
  than registration would be the way in. The frontend has to match this minimum.
- **Credential lifetimes are constants, not env vars** (`CredentialTtl`: magic link 15 min, password
  reset 30 min, invitation 7 days). They are product rules, not per-host tuning.
- **Account enumeration.** Magic-link and password-reset requests answer `{ accepted: true }` for
  every address, registered or not. `POST /auth/register` and `POST /invitations` deliberately do
  *not*: both return `CONFLICT` for an address that already has an account or a membership. That is
  a knowing trade — registration needs to tell the user why it failed, and inviting is an
  authenticated admin action inside one space — and it is the only enumeration surface left.
- **Authorization is declared, not remembered.** `@Roles(SpaceMemberRole.admin)` plus a global
  `RolesGuard`; `POST /invitations` is the first route to use it, and the DVR, member, routing and
  destructive-configuration routes from T05/T06 attach the same decorator. Both new guards throw
  rather than fall open when a request carries no user, so global guard registration order cannot
  turn either into a no-op.
- **One canonical sensitive-field list.** `src/cross/common/sensitive-fields.ts` is now read by both
  the Pino formatter and Sentry's scrubbers, matched case-insensitively, and covers `password`,
  `passwordHash`, `token`, `accessToken`, `refreshToken` and `faceToken` on top of the previous four
  names.
- **Routing defaults have one definition.** `ALERT_ROUTING_DEFAULTS` moved into
  `src/cross/common/constants.ts`; `prisma/seed.ts`, registration and the e2e fixture all read it, so
  a seeded space and a registered one cannot start with different matrices.

## Design decisions (T05)

- **The recorder is a port, not a protocol.** `DvrClientPort` has exactly two operations —
  list the channels, pull one channel's frame. When T05 shipped, `HttpDvrClientService` spoke a
  placeholder JSON contract (`GET {url}/api/channels`, `GET {url}/api/channels/{id}/snapshot`)
  because no appliance had been chosen. It now speaks Hikvision ISAPI against the real recorder —
  see "Hikvision ISAPI client" below. Poll-versus-push is still undecided and still one provider
  swap, and the e2e suite overrides the port instead of needing an appliance.
- **Listing the channels *is* the connectivity test.** A recorder that answers with its channel list
  is reachable and accepted the password, so there is no separate probe to keep in sync. A 401/403
  is answered as `VALIDATION_ERROR`, not `UPSTREAM_ERROR`: the recorder is up, the configuration the
  operator just submitted is what is wrong.
- **A configuration that cannot be reached is never stored.** `PUT /dvr` discovers first. Storing it
  anyway would leave the space pointing at a recorder nothing can poll, with the previous working
  credentials already overwritten.
- **Rediscovery no longer overwrites the camera name.** T03's reconciliation refreshed `name` and
  `location` from the recorder on every pass, which silently undid an operator rename — and
  `DATA_MODEL_REQUIREMENTS.md` makes both operator-editable, defaulting to the DVR name. Discovery
  now supplies them when a channel first appears and refreshes only `status` afterwards. The T03
  integration test asserted the old behavior and was updated with it.
- **`isConfigured` is derived, never sent.** A full-frame camera is configured exactly while it
  carries an `alertType`; a partial one exactly while it has at least one zone. Zone creation and
  deletion recompute it, so deleting the last zone disarms the camera instead of leaving it polled
  with nothing to evaluate.
- **Freshness and evidence are different questions.** `lastSnapshotAt` records the last frame the
  recorder handed over — every successful capture updates it, along with `status` — while the stored
  `snapshots` rows are the frames an alert was raised on plus the ones an operator asked for. Storing
  every poll tick would write a BLOB every `POLLING_INTERVAL_SECONDS` per camera, and snapshot
  retention is explicitly deferred.
- **The pipeline decides the alert level.** Full-frame cameras evaluate one implicit area carrying
  `Camera.alertType`, partial ones evaluate their zones' own levels, and both go through the same
  hysteresis. What comes out is an `AlertCandidate`; T06 introduces persistence, broadcast and
  routing with their first implementation.
- **One poll interval for the process, not one per camera.** The per-camera `pollingIntervalSeconds`
  column is gone with the setup-era schema. The scheduler re-reads each tick which spaces own a
  recorder and which of their cameras are pollable, so a newly configured space is picked up without
  a registry of timers that can go stale.
- **Uploads are validated by magic number.** `POST /cameras/:id/analyze` checks the file signature
  and falls back to the declared type only when `file-type`'s ESM entry point cannot be loaded (which
  is the case under Jest). A client that labels a script `.jpg` does not reach the detector.
- **Rectangle bounds are enforced three times** — DTO decorators (range and two decimal places), the
  service (the merged rectangle, so moving `x` alone cannot push a zone past the frame edge), and the
  `monitor_zones_rectangle_bounds_check` constraint in MySQL. `ErrorCode.INVALID_POLYGON` became
  `INVALID_ZONE`; polygons no longer exist.
- **Camera reads are ordered by `externalId`.** The dashboard grid renders in list order, and the
  UUID primary key gives an arbitrary one that reshuffles as cameras come and go.
- **API stays on `/api/v1`.** T04 already shipped breaking auth shapes there, no released consumer
  exists, and the frontend contract arrives with this schema, so a `/v2` split would version nothing.
  T07 owns the final call and should record it explicitly.

## Configuration added (T05)

- `DVR_TIMEOUT_MS` (default 5000) — connectivity test and channel discovery.
- `POLLING_INTERVAL_SECONDS` (default 5) — one tick for the process; cameras have no per-camera interval.

  the write has already cost a recorder round trip and a detection call.

## Design decisions (T06)

- **The pipeline records; its callers do not.** `PipelineService.processImage` hands its candidates
  to `AlertEventsService.record` after the frame is evaluated, so the poll tick and the manual
  `POST /cameras/:id/analyze` cannot disagree about what got persisted. `AnalysisResult` still
  carries the candidates, unchanged, for the synchronous answer.
- **The socket is scoped by room, not by filter.** The gateway authenticated the handshake and then
  called `server.emit`, which is every connected client. With one tenant that was the audience; with
  `spaces` it is a cross-tenant leak, and the one place in this API where scoping is not a `where`
  clause. A socket now joins `space:<spaceId>` taken from its own verified claims, a token carrying
  no `spaceId` is disconnected rather than parked in no room, and `broadcast` takes the space id.
- **Keyset paging, not `skip`.** The cursor is the `(detectedAt, id)` tuple the history index is
  ordered by, base64url-encoded and opaque. `id` is not decoration: one detection frame writes an
  event per entered area with an identical `detectedAt`, so a timestamp-only cursor skips or repeats
  the siblings. The query asks for one row past the page and uses its presence as "there is more",
  rather than counting the highest-volume table twice.
- **A cursor the API did not issue is a 400.** Silently paging from the start would answer a
  corrupted client with plausible, wrong data.
- **The correlation id leaves the process only towards a provider.** It is absent from
  `EventDeliveryDto`, from `openapi.json`'s response schemas, and it was already in
  `SENSITIVE_FIELD_NAMES`. Returning it to a member would let them acknowledge an alert they never
  received, since the acknowledgement route has nothing else to authenticate.
- **One correlation id per attempt, from the CSPRNG.** Two recipients sharing one would make either
  of them the acknowledger of the other's reply.
- **The acknowledgement route answers the same three ways.** A match, a repeat and an unknown id all
  get `202 { accepted: true }` — the shared `AcknowledgementDto` the magic-link and password-reset
  requests already use. The route is unauthenticated because no webhook authentication scheme is
  chosen yet, so its answer must reveal no event.
- **One inbound callback, one transaction.** `consumeInbound` claims the delivery
  (`inboundReceivedAt: null`) and acknowledges its event (`acknowledgedAt: null`, so the first
  responder wins) inside one `$transaction`. Split in two, a failure between them records a reply
  the history never shows as acknowledged.
- **Deliveries are planned, not sent — a deliberate deviation from plan step 5.** No sender port
  ships here. The PR #42 review removed exactly such a port (`alert-emitter.port.ts` plus its
  logging placeholder) for having no caller, and adding it back with still no provider would earn
  the same finding. Rows are written `pending`; the interface arrives with the provider that needs
  it, and nothing in this task's DoD depends on sending. Plan step 5's constraint — no provider
  hard-coded into the data model — holds either way.
- **No manual acknowledgement route.** `DATA_MODEL_REQUIREMENTS.md` shows no such control on the
  history screen and the plan specifies acknowledgement through an inbound provider reply. A member
  route can be added when the UI asks for one; it is a new route, not a silent behavior.
- **`AlertEvent.acknowledgedAt` is the event, not the attempt.** A second reply on another channel
  still records its own delivery row and its own `inboundReceivedAt`; it does not rewrite who
  acknowledged the alert.

## Hikvision ISAPI client

Replaces the placeholder JSON contract in `HttpDvrClientService` with the protocol the appliance
actually speaks. Verified against the recorder on the bench: a DVR-208G-M1, firmware V4.71.410,
eight BNC inputs, no IP channels.

- **Digest, not basic.** ISAPI answers `401` with a `WWW-Authenticate: Digest` challenge and accepts
  nothing else, so `auth: { username, password }` never had a chance. Every call is now the
  unauthenticated probe followed by the signed retry, hand-rolled over `node:crypto` (RFC 7616, MD5
  and SHA-256, `qop=auth`). No dependency was added: `DEPENDENCIES.md` asks for a security review of
  anything touching auth, and the signing is shorter than the review would be. `-sess` algorithms and
  `auth-int` are refused rather than guessed at — an unsigned attempt is reported as "no supported
  authentication scheme", never as a rejected password.
- **A 401 no longer means bad credentials on its own.** Only the *signed* attempt getting refused is
  a `VALIDATION_ERROR`; the challenge that opens every exchange is expected traffic.
- **Two id schemes, one stored.** `/ISAPI/System/Video/inputs/channels` speaks the BNC port number
  (`1`..`8`); `/ISAPI/Streaming/channels` wants port and stream glued together (`401` is port 4, main
  stream). `externalId` stores the port — the physical socket an operator can point at — and the main
  stream is derived. `externalId` is validated against `/^\d{1,2}$/` before it reaches a request path,
  because a stored identifier is still external input.
- **`resDesc` is the only signal detector.** `videoInputEnabled` reads `true` on all eight ports
  whether a camera is wired or not, and an empty port still answers the snapshot endpoint with HTTP
  200 and a ~10 KB "NO VIDEO" placeholder JPEG. The listing decides `status`, never the snapshot
  status code.
- **Regex instead of an XML parser.** Three fields out of one fixed vendor schema. A parser
  dependency over untrusted input would owe a security review for more code than it replaces; the
  five XML entities are decoded because channel names are operator-editable.
- **An empty roster is an error, not an empty result.** A recorder with zero video inputs does not
  exist, so a listing that parses to nothing means the body was not the listing. Reporting success
  would hand `reconcileDiscovery` an empty set and unconfigure every camera in the space.
- **The signed `uri` comes from the URL, not from the path constant.** A recorder configured with a
  base URL that carries its own path prefix puts that prefix on the request line, and a digest that
  covered only the ISAPI suffix would be refused for looking wrong rather than for a wrong password.
- **First parameter wins when the challenge lists a second scheme.** `Basic` and `Digest` share
  parameter names, and a `Basic realm=...` trailing the Digest challenge must not overwrite the realm
  being signed.
- **A username with a control character is a 400 at submit time.** It could never be carried in a
  digest header, so `ConfigureDvrDto` refuses it outright rather than letting discovery fail with an
  opaque upstream error much later.
- **The listing transfer is capped too.** Snapshots have a tunable byte limit; the listing gets a flat
  1 MB one, so a probe answered with a stream instead of a document cannot be buffered without
  bound.

Verification: all six repo checks green — `npm run test:all` 49 unit suites / 356 tests, 2
integration suites / 25 tests, 6 e2e suites / 52 tests. Plus a run of the real client against the
bench recorder: all eight ports listed with the four wired ones online, a 704x576 `image/jpeg`
pulled from port 3 (`file`-verified), a wrong password answered `VALIDATION_ERROR "DVR rejected the
supplied credentials"`, and `4/../../System/deviceInfo` refused before any request left the process.

Not done, deliberately:

- **Snapshot resolution is stuck at 704x576.** ISAPI ignores `videoResolutionWidth`/`imageQuality` on
  this firmware; native resolution needs a frame pulled off RTSP. Out of scope until the product asks
  for it.
- **No "NO VIDEO" placeholder detection on the snapshot path.** The only tell is a fixed byte size,
  which is fragile. Discovery already marks those ports offline.
- **The nonce is not cached.** One challenge per request. Caching means tracking nonce expiry and a
  counter per recorder; on a LAN that state costs more than the round trip. Marked `ponytail:` in the
  source with the upgrade path.
- **Existing fixtures still use `'ch1'`-style channel ids.** They exercise mocked ports, not this
  client, so they pass — but they no longer look like anything a real recorder returns.

## Live frame per camera (front-end feedback)

The UI needs a picture for a camera that never alerted: a thumbnail plus a freshness clock on the
dashboard, and a backdrop to draw zones on. Until now a frame was only written when it was evidence,
so a quiet camera had none.

- **One row per camera, rewritten in place.** `Snapshot.isLive` marks it, `SnapshotAccessorService.upsertLive`
  writes it, and every successful poll refreshes it (`PollingScheduler.pollOnce`). A new row per tick
  was the alternative and it is unbounded growth: snapshot retention is still not solved, so the one
  path that runs forever is the one that must not add rows. The refresh runs *after*
  `PipelineService.processImage` and its `Either` failure is recorded on the camera's status: a
  thumbnail write must never be able to suppress an alert, and a silently dropped result would show
  up only as a thumbnail that stops refreshing.
- **Evidence rows stay immutable.** An alert's frame must still show what the alert saw, so the
  pipeline keeps creating its own row. A marker column rather than "the row no alert references":
  the latter would let a poll delete an evidence row in the window between storing it and the
  `AlertEvent` insert that points at it.
- **`POST /cameras/:id/snapshots` writes the live row too.** What the operator asked for is this
  camera's current frame, and a row per button press is growth with no retention behind it.
- **No new route.** `latestSnapshotUrl` on the camera read already resolves to the newest frame, and
  the live row is always the newest — `GET /cameras/:id/snapshots/latest` would answer the same id.
  The contract did not move: `npm run openapi:export` produces no diff.

Verification: all six checks green — `npm run test:all` 49 unit suites / 364 tests, 2 integration
suites / 26 tests, 6 e2e suites / 52 tests. The integration case drives the real MySQL path: two
`upsertLive` calls for one camera keep one row with the second frame's bytes, and another space's id
answers `null`.

Not done, deliberately:

- **Unconfigured cameras still get no frame from polling.** `findPollableBySpace` only returns
  configured, enabled cameras, so a channel nobody monitors is never captured — including a partial-mode
  camera before its first zone exists, which is exactly the zone editor's case. The on-demand
  `POST /cameras/:id/snapshots` covers it. Widening the capture pass to every enabled camera is a DVR-load
  decision, not a code detail, so it waits for the product to ask.
- ~~**`Cache-Control: private, max-age=60` outlives an overwrite.**~~ Fixed: the route now sends
  `private, no-cache` with the frame's stored sha256 as the `ETag`, so the browser keeps its copy but
  revalidates every read and an unchanged frame costs a 304 instead of the BLOB. A client no longer
  has to ask with `cache: 'no-store'` to see the new bytes.
- **No DB constraint enforces one live row per camera.** MySQL 8 has no partial unique index, and the
  writer is a single accessor method; two rows would only cost an extra frame, not correctness.

## Live HLS stream per camera (front-end feedback)

The dashboard needs moving video while the pointer is over a camera. Snapshots stay where they are —
the configuration screens and the zone editor keep reading the stored frame. This closes the "live
streaming" line the plan deferred: protocol, authorization and URL contract are all decided in
[`docs/decisions/002-hls-live-streaming.md`](../docs/decisions/002-hls-live-streaming.md).

- **The backend never touches a media packet.** RTSP from the recorder into MediaMTX, HLS out to
  `hls.js`. `GET /cameras/:id/live` authorizes the camera, registers its path through MediaMTX's
  Control API and answers `{ protocol, url }`. MediaMTX's own `sourceOnDemand` starts the RTSP pull
  when the first reader asks for the playlist and drops it when the last one leaves, so "activate
  only on demand" cost a config flag and no process management. No transcoding, no ffmpeg.
- **`replace`, not `add`.** MediaMTX's `add` fails on an existing path, and the second viewer of a
  camera is the normal case. `POST /v3/config/paths/replace/{name}` creates or overwrites, so the
  publish call is idempotent with no read first.
- **The URL is not the credential, so there is no URL secret and no expiry to renew.** The path name
  is the camera id. MediaMTX runs `authMethod: http` against `POST /api/v1/streaming/authorize`, so
  every playlist and every segment is authorized separately, with the caller's ordinary access token
  attached as a header through `hls.js`'s `xhrSetup`. Nothing new is minted: the access token is the
  clock, and the frontend already refreshes it.
- **One token verifier, not two.** The hook's token arrives in a JSON body, where no guard can reach
  it, so `verifyAccessToken` (`src/cross/common/access-token.ts`) was lifted out of `JwtAuthGuard`
  and both now call it. Two verifiers of the same credential drift, and that drift is a hole rather
  than a bug. The guard's four rejection messages are unchanged — it maps the `Either` the helper
  returns, which is why `buildGuardException`'s `message` is now optional.
- **`publish` is refused before the token is even read.** A granted publish would let a caller push
  their own video into a camera's path, and the dashboard would render it as that camera's feed. Only
  `read` over `hls` is authorized.
- **The hook declares every field MediaMTX sends.** The global pipe runs `forbidNonWhitelisted`, so
  one undeclared field turns the hook into a 400 and MediaMTX, seeing anything but 200, locks out
  every viewer. There is an e2e canary that posts the full ten-field payload.
- **`source` joined `SENSITIVE_FIELD_NAMES`.** MediaMTX names a path's upstream `source`, and ours
  carries the recorder password in its userinfo. The publish call is outbound so `pino-http` never
  sees it, but an axios error carries the body it was sent with — so `publish` returns `Either`
  instead of letting anything throw with that attached, and the field name is redacted on both egress
  channels anyway.
- **`isConfigured` is deliberately *not* a gate here**, unlike the detection pipeline: a camera with
  no monitor configuration is exactly the one an operator is about to configure, and they need to see
  it to draw a zone. `status` is not a gate either — it is a poll-time observation, and polling is off
  by default in dev, so gating on it would refuse every working camera on a developer's machine.
  `isEnabled` is the one switch that still refuses.
- **Two env knobs instead of two columns.** RTSP is a separate service on a separate port from the
  stored ISAPI base URL, and `/Streaming/Channels/302` is BNC port 3, sub-stream. `DVR_RTSP_PORT`
  (554) and `DVR_RTSP_STREAM` (`sub`) are env vars because a space owns one recorder and none of them
  moves 554. The sub-stream is the default: the recorder's uplink carries every viewer.

Verification: all six repo checks green — `npm run test:all` 52 unit suites / 421 tests, 2 integration
suites / 26 tests, 6 e2e suites / 70 tests. `npm run openapi:export` committed with the routes.
The e2e proves the two halves that matter: the response carries no recorder password while the fake
publisher records that the credential did reach the media server, and a token from another space
answers 404 on both the live URL and a segment authorization.

Not done, deliberately:

- **Reachability is unsolved and is not code.** The recorder is on a home LAN behind NAT, so a
  MediaMTX outside that network cannot see it; today both run on the same LAN, which is why this
  ships working. Exposing port 554 to the internet is not the fix — these recorders are scanned for
  continuously and this firmware is old. A tunnel (WireGuard, Tailscale) into the recorder's network
  is, and it belongs to whoever provisions the media server.
- **Codec unverified.** Passthrough holds only while the channel is H.264, which this firmware should
  be. One command settles it on the bench: `ffprobe rtsp://…/Streaming/Channels/302`. An H.265
  channel would need transcoding, which is CPU per stream and stays unbuilt until one demands it.
- **Nothing removes a MediaMTX path.** A camera published once keeps its path after it is logically
  deleted. The path is inert — the hook refuses every reader whose camera no longer resolves — but the
  entries accumulate in the media server's config. Marked `ponytail:` in the publisher.
- **Latency is stock HLS**, several seconds. Accepted; Low-Latency HLS brings it to roughly 2–3s and
  is a MediaMTX flag, not code.
- **No `/health/dependencies` entry for the media server.** Streaming being down must not mark the app
  unready, and the existing indicator covers face-auth only. Worth adding when streaming is load-bearing.
