# 04 — Hardening & Pipeline Quality: tu-seguridad-back

> Implementation plan closing the open audit findings and the alert-quality gaps left by plan 03.
> Audience: an AI coding agent (or developer) implementing tasks T01–T11 in order.
> Each task has a **Definition of Done (DoD)**: exact commands and observable results. A task is
> complete only when every DoD item passes.

## 1. Context

Plans `01`–`03` shipped the product: NestJS 11 with layered accessors and `Either` errors, the
tenant/alert data model, DVR discovery and ISAPI capture, the detection pipeline with its cadence
ladder, alert emails with burned-in detection boxes, HLS live streaming, and the ops layer
(circuit breaker, Prometheus, Sentry, OTel sidecar, CD, health split, committed `openapi.json`).

What is left is not a new capability, it is the second half of the ones that exist. Three sources
feed this plan:

- [`docs/AUDIT_BACKLOG.md`](../docs/AUDIT_BACKLOG.md) — one P0 and three P1 items are still open.
- [`docs/STANDARDS_GAPS.md`](../docs/STANDARDS_GAPS.md) — the check/gate gaps that make CI weaker
  than it reads.
- [`README.md`](../README.md) Roadmap — the items plan 03 explicitly deferred: retention, detection
  cooldown, delivery retry, per-camera tuning, DVR capture reliability.

Scope decisions confirmed by the repo owner before writing this plan:

- **Deployment stays single-host, PM2 fork mode, one tenant.** Nothing here may assume a second
  process. In-memory state (`CameraStatusRegistry`, `CadenceEngine`, `OccupancyEngine`,
  `LiveStreamService`'s memo) stays in memory.
- **Redis, Docker, and a queue stay declined** — same cost reason as plan 02 §1. Every task below
  runs on the host as it is: no new service, no new managed dependency. Where a job is needed,
  `@nestjs/schedule` is already installed and already owns one interval.
- **Balanced scope.** Security and scale items ship alongside the alert-quality features, ordered by
  risk × effort rather than by category.

Two housekeeping notes, both from the audit, that apply before the first commit:

- `docs/AUDIT_BACKLOG.md` #59 and #61 are marked FIXED and merged (#75). #71 claims three plan-02
  tasks are marked done but are not on `develop` — verify against `develop` before trusting either
  tracker, and correct the tracker in the same commit as T11 if the claim still holds.
- `npm audit --omit=dev` currently reports **6 high** advisories (all reachable through
  `@nestjs/swagger`'s bundled `js-yaml`). The gate is set to `critical`, so CI is green and the

## 2. Stack additions

**None.** Every task is built from what is already installed:

| Concern | Built from | Why not something else |
|---|---|---|
| Upload bound | `multer`'s `limits` (already there via `FileInterceptor`) | The size check exists, it just runs after the buffer. Moving it earlier costs an options object. |
| Retention sweep | `@nestjs/schedule` `@Cron` | Already a dependency, already runs the poll interval. A queue for a nightly `DELETE` is infrastructure for its own sake. |
| Delivery retry | The `event_deliveries` row that already records the outcome | The row is the queue. It has a status, a timestamp and an error column. BullMQ was declined in plan 02 and nothing has changed. |
| Constant-time auth | `bcrypt.compare` against a fixed dummy hash | No library computes this for us and none needs to. |
| Cooldown / dedup | `AlertEvent` rows already keyed by camera and type | A per-camera in-memory window is one `Map`, and the hysteresis cycle it guards is already in `OccupancyEngine`. |

Add no dependency in this plan. If a task appears to need one, stop and flag it.

## 3. Conventions (in addition to `AGENTS.md` and `.standards/`)

- Every new env var lands in `EnvNames` (`src/cross/common/constants.ts`), the Joi schema
  (`src/cross/config/env-validation.schema.ts`), `.env.example`, and the README env table — in the
  same commit. Dev default where safe, `required()` in production otherwise. `.env` itself is the
  owner's to edit: hand over the lines, never write the file.
- Every new job or sweep is **opt-out by env var and a clean no-op when disabled**, same posture as
  `OTEL_ENABLED` and `POLLING_ENABLED`. Local dev must not start deleting rows because someone ran
  `npm run start:dev`.
- Anything that deletes rows is **logical or bounded**: a sweep names its predicate in full, caps
  its batch, and logs the count it removed. No `deleteMany` without a `where` and a limit.
- A new secret-bearing field lands in `SENSITIVE_FIELD_NAMES` in the commit that introduces it.
- API surface changes (new DTO field, new route, new `@Api*`) require `npm run openapi:export` and
  the regenerated `openapi.json` in the same commit.
- One Conventional Commit per task, English, no agent trace.

## 4. Tasks

### T01 — Bound the upload before it is buffered

**Closes:** `AUDIT_BACKLOG` #58 (P0).

**Problem:** `POST /cameras/:id/analyze` uses `@UseInterceptors(FileInterceptor('file'))` with no
options (`src/modules/cameras/cameras.controller.ts:277`). Multer's default storage is memory and
its default size limit is unlimited, so the whole body is resident before
`cameras.service.ts:153` ever reads `SNAPSHOT_MAX_BYTES`. One authenticated caller posting a large
file takes the process down, and the process is the whole product.

**Steps:**
1. Pass `limits: { fileSize: <SNAPSHOT_MAX_BYTES>, files: 1 }` to `FileInterceptor`. The value comes
   from config, so the interceptor is constructed through a factory that reads `ConfigService`
   rather than a literal — the existing `@UseInterceptors(FileInterceptor('file', {...}))` form
   takes a static object, so use `MulterModule.registerAsync` on the module that declares the
   controller, or a small mixin interceptor. Whichever lands, the limit and the service check read
   the same env var; two numbers drift.
2. Multer throws `LIMIT_FILE_SIZE` as a `PayloadTooLargeException` past the limit. Confirm it
   surfaces through `EitherInterceptor` as a mapped `HttpException` and **not** as the unexpected-500
   branch — an oversized upload is a client error and must never reach Sentry.
3. Map it to the existing `VALIDATION_ERROR` shape (or add `PAYLOAD_TOO_LARGE` to `ErrorCode` if the
   413 status is worth its own code — decide once, document in the controller's `@ApiFailures`).
4. Keep the in-service size check. It is the one that still runs for the pipeline's own captures.

**DoD:**
- [ ] `curl -F file=@<file larger than SNAPSHOT_MAX_BYTES>` returns 413 (or the chosen mapped status)
      and the process RSS does not grow by the file size (`pm2 monit` or `/proc/<pid>/status` before
      and after).
- [ ] A unit spec asserts the limit is read from `SNAPSHOT_MAX_BYTES`, not hard-coded.
- [ ] An e2e spec posts an oversized file and asserts the status and the error code.
- [ ] Sentry receives nothing for that request (assert the interceptor branch in a unit spec —
      `captureException` not called).
- [ ] `npm run openapi:export` re-run; `openapi.json` committed if the failure list changed.
- [ ] Commit `fix(cameras): bound the analyze upload before it is buffered`.

### T02 — Gate Swagger, and make rate limiting real

**Closes:** `AUDIT_BACKLOG` #62 and #63 (P1).

**Problem, two halves:**
- `setupSwagger(app)` in `main.ts` is unconditional, so `/docs` and `/docs-json` serve the full route
  inventory in production to anyone who asks.
- `createThrottlerOptions` carries `skipIf: () => NODE_ENV !== 'production'`, so every non-production
  environment — including staging — has no rate limit at all, and no route ever tightens the global
  ten-per-second. Login, password reset, magic link and `POST /events/acknowledgements` are all
  `@Public()` and all get the same allowance as a camera list.

**Steps:**
1. New env var `SWAGGER_ENABLED`, defaulting to `true` outside production and `false` in production.
   `setupSwagger` is called only when it is on. `scripts/export-openapi.ts` must keep working
   regardless — it builds the document directly and never calls `setupSwagger`, so verify rather
   than assume.
2. Delete `skipIf`. Rate limiting is on in every environment. If a test suite needs it off, the
   suite overrides the guard — the production config must not carry a test convenience.
3. Add per-route `@Throttle` overrides, tighter than the global default, on:
   `POST /auth/login`, the four `@Public()` credential-recovery routes, `POST /invitations/accept`,
   the public face-identity route, and `POST /events/acknowledgements`.
   Pick one number per class (an interactive credential attempt is not a webhook) and state it in
   the controller comment beside the decorator.
4. Leave `@SkipThrottle()` on `POST /streaming/authorize` — the media server calls it once per
   segment from one IP, and ADR 002 already argues why.
5. `THROTTLER_REJECTIONS_TOTAL` already counts 429s. Confirm the counter still increments through
   the per-route override (the metrics guard extends the throttler guard; a route-level override
   must not bypass it).

**DoD:**
- [ ] `NODE_ENV=production npm run start:prod` → `GET /docs` returns 404; with `SWAGGER_ENABLED=true`
      it returns 200.
- [ ] An e2e spec drives more than the per-route limit against `POST /auth/login` and asserts 429.
- [ ] `curl /metrics` (with the token) shows `throttler_rejections_total` moved after that spec.
- [ ] `npm run openapi:export` produces the same `openapi.json` (throttling is not in the contract).
- [ ] `.env.example`, README env table and the Joi schema all carry `SWAGGER_ENABLED`.
- [ ] Commit `fix(security): gate swagger in production and tighten auth rate limits`.

### T03 — Answer identically for a registered and an unregistered address

**Closes:** `AUDIT_BACKLOG` #60 (P1).

**Problem:** `DATA_MODEL_REQUIREMENTS.md` mandates that magic-link, password-reset and invitation
flows answer identically whether the address is registered. The *body* does. The *timing* does not:
an unknown address returns before any hash is computed, a known one waits out a bcrypt compare. The
difference is measurable over a handful of requests, and it turns those routes into an account
enumeration oracle.

**Steps:**
1. In `PasswordHashService`, add a `compareWithDummy()` (or equivalent) that runs a bcrypt compare
   against a fixed hash generated at module init with the same cost factor the real hashes use.
2. Every path that would return early because the user does not exist calls it before returning:
   `AuthService` login, `CredentialRecoveryService`'s request paths, the invitation-accept lookup.
3. Do the same audit for the token paths — a token that fails its lookup must cost the same as one
   that fails its comparison.
4. This is timing mitigation, not a constant-time guarantee. Say so in the comment: the aim is to
   remove the *large* signal (hash / no hash), not to defeat a lab-grade measurement, and the rate
   limits from T02 are the other half of the answer.

**DoD:**
- [ ] A unit spec asserts the dummy compare is invoked on the not-found branch of each route.
- [ ] A crude local measurement (100 requests each, known vs unknown address) shows the medians
      within noise of each other; record the two numbers in the tracker.
- [ ] The response bodies are unchanged — the existing specs asserting identical answers still pass.
- [ ] Commit `fix(auth): equalise the cost of a lookup that finds nothing`.

### T05 — Retention: nothing currently deletes anything

**Closes:** `AUDIT_BACKLOG` #66; README Roadmap "snapshot retention"; ADR 001 "retention must be
added before table growth becomes material".

**Problem:** there is no `@Cron` anywhere in `src/`, and no `deleteMany` outside the test truncation
helper. Consumed and expired `auth_tokens` rows accumulate forever. So do expired invitations. So do
evidence snapshots — `MEDIUMBLOB` rows, one per alert, on the same MySQL instance that serves every
query. The live-frame write is throttled (`SNAPSHOT_LIVE_WRITE_SECONDS`) and bounded to one row per
camera, so live frames are not the growth; evidence frames are.

**Steps:**
1. New `RetentionService` under `src/modules/` (its own small module, wired into `AppModule`), with
   one `@Cron` at a quiet hour. Gated by `RETENTION_ENABLED` (default `false` in dev).
2. Three sweeps, each with its own env-configured window, each capped at a batch size per run, each
   logging the count it deleted:
   - `auth_tokens` where consumed or expired past `RETENTION_TOKEN_DAYS`.
   - `invitations` where expired or accepted past `RETENTION_INVITATION_DAYS`.
   - `snapshots` where `isLive = false`, older than `RETENTION_SNAPSHOT_DAYS`, **and** not referenced
     by an `AlertEvent` that is inside the retention window.
3. The snapshot sweep is the one with a foot-gun: `Snapshot.camera` is `onDelete: Restrict` and
   `AlertEvent.snapshotId` is `SET NULL`. Deleting a snapshot an event still points at nulls the
   event's frame and leaves the event — which is the intended outcome (the event is the record, the
   frame is the evidence), but it must be a decision written down, not a side effect discovered
   later. State it in the service comment and in `ARCHITECTURE.md`.
4. New accessor methods only — no `PrismaService` in the module (`grep -rn "PrismaService"
   src/modules/` must stay empty).
5. Expose a counter per sweep (`retention_rows_deleted_total{sweep}`) so a sweep that silently stops
   is visible.

**DoD:**
- [ ] Integration spec per sweep: seeds rows either side of the window, runs the sweep, asserts
      exactly the old ones are gone and the in-window ones remain.
- [ ] Integration spec asserting an `AlertEvent` whose snapshot was swept survives with
      `snapshotId = null`.
- [ ] `RETENTION_ENABLED=false` (the dev default) does zero queries — assert the accessor is not
      called.
- [ ] Batch cap honoured: seed more than one batch, assert one run deletes at most the cap.
- [ ] `/metrics` shows the new counter.
- [ ] `ARCHITECTURE.md` gains a "Retention" section; README env table updated.
- [ ] Commit `feat(retention): sweep expired tokens, invitations and evidence snapshots`.

### T06 — Prune the per-camera state a deleted camera leaves behind

**Closes:** `AUDIT_BACKLOG` #65; ADR 002 open item "Path cleanup".

**Problem:** a camera is deleted logically (`deletedAt`), and five in-memory maps keep its entry
forever: `CameraStatusRegistry.statuses`, `CadenceEngine.cameras`, `PollingScheduler.liveWriteDueAt`,
`OccupancyEngine.states` (keyed per zone), `LiveStreamService.recentAuthorizations`. Sixth: MediaMTX
keeps the path registered for a camera nobody can read any more
(`mediamtx-stream-publisher.service.ts:24` says so in a `ponytail:` comment).

Individually each is a few bytes and the process restarts often enough that nobody notices. Together
they are the reason a camera that comes *back* (same id, un-deleted) inherits a cadence and an
occupancy state from before it left — which is a correctness bug, not a memory one.

**Steps:**
1. One `forget(cameraId)` per holder. The camera-delete path calls each of them. Prefer an explicit
   list of calls in `CamerasService.softDelete` over an event bus: five call sites, one file,
   readable at 3am.
2. `OccupancyEngine` is keyed per zone, so zone delete needs the same treatment, and camera delete
   forgets every zone of that camera.
3. MediaMTX: delete the path on camera delete, best-effort. It must never fail the delete — the
   camera is gone from the API either way, and the hook already refuses readers, so a leftover path
   is inert. Log the failure, do not propagate it.
4. While in there: a camera whose `deletedAt` is later cleared (if that path exists at all) must
   start from a clean cadence. If no such path exists, say so in the comment and move on.

**DoD:**
- [ ] Unit spec per holder: entry present, `forget`, entry gone.
- [ ] Unit spec asserting `CamerasService.softDelete` calls all of them.
- [ ] Unit spec asserting a MediaMTX failure on delete leaves the delete successful.
- [ ] e2e: delete a camera, assert `GET /cameras/:id/status` no longer reports a stale poll level.
- [ ] The `ponytail:` comment in `mediamtx-stream-publisher.service.ts:24` is removed, not amended.
- [ ] Commit `fix(cameras): forget per-camera state when a camera is deleted`.

### T07 — Detection cooldown, so one intruder is one alert

**Closes:** README Roadmap "detection cooldown/dedup (no burst suppression, one alert per hysteresis
cycle)".

**Problem:** the hysteresis in `OccupancyEngine` already collapses a flickering detection into one
cycle, which is the *frame-level* protection. What is missing is the *event-level* one: a person who
stays in a zone for twenty minutes, leaves the frame for one poll and comes back, produces a second
alert — and at the detection cadence that is a mail every couple of minutes. The recipient stops
reading them, which is the actual failure.

**Steps:**
1. A per-`(cameraId, zoneId, alertType)` cooldown window, `ALERT_COOLDOWN_SECONDS`, consulted in
   `PipelineService` after the candidate is raised and before the `AlertEvent` is written.
2. In memory, a `Map`, same posture as every other pipeline map — single process, and a restart
   losing the window costs at most one duplicate alert.
   `ponytail: in-memory window, lost on restart; move to a column if a restart storm ever matters.`
3. A suppressed candidate is **counted, not silent**: `pipeline_alerts_suppressed_total{cameraId}`,
   and one debug log line. An alert that never fired and left no trace is indistinguishable from a
   detection that never happened.
4. The cooldown must not suppress a *different* alert type on the same zone — an `intruder` after a
   `suspicious` is new information.
5. `0` disables it, for the same reason `SNAPSHOT_LIVE_WRITE_SECONDS` accepts `0`.

**DoD:**
- [ ] Unit spec: two candidates inside the window produce one `AlertEvent`; the second is counted.
- [ ] Unit spec: two candidates either side of the window produce two events.
- [ ] Unit spec: a different `alertType` inside the window is not suppressed.
- [ ] `ALERT_COOLDOWN_SECONDS=0` produces the current behaviour (existing pipeline specs pass
      unchanged with it unset).
- [ ] `/metrics` shows the suppression counter.
- [ ] README "Detection pipeline" documents the window; env table updated.
- [ ] Commit `feat(pipeline): suppress repeat alerts inside a per-zone cooldown`.

### T08 — Alert delivery: retry the failures, drain the pending

**Closes:** README Roadmap "alert-email retry + drain of pending on crash".

**Problem:** `AlertEmailService` is called without `await` (deliberately — a relay outage must not
stall detection) and `alert-email.service.ts:95` carries `ponytail: serial, no retry, no queue`. A
relay hiccup makes an `event_deliveries` row `failed` and nothing ever tries again. A crash between
the row being written and the send completing leaves it `pending` forever — indistinguishable from
the `call` and `whatsapp` rows that are `pending` because nobody ever built a sender.

**Steps:**
1. Distinguish "pending because no sender exists" from "pending because the send did not finish".
   The channel already tells them apart (`email` has a sender, `call`/`whatsapp` do not), so the
   sweep filters on channel rather than needing a new column. State that in the service comment —
   it is the reason no migration is needed.
2. A `@Cron` in the same `RetentionService` module as T05 (one scheduled-jobs module, not two),
   gated by `DELIVERY_RETRY_ENABLED`: pick up `email` deliveries that are `failed` or `pending`,
   older than `DELIVERY_RETRY_DELAY_SECONDS`, with fewer than `DELIVERY_RETRY_MAX_ATTEMPTS` attempts,
   and re-send.
3. Attempt counting needs somewhere to live. Prefer a migration adding `attempts Int @default(0)` to
   `EventDelivery` over inferring it from the error text — the column is cheap and the inference is
   a bug waiting to happen. Add the table to `test/utils/truncate-all.ts`'s order if the migration
   changes anything there (it does not — same table).
4. Reuse `markSent`/`markFailed` exactly as they are. Their `status: pending` guard is what stops a
   retry from overwriting an acknowledgement that arrived while the retry was in flight — do not
   loosen it, and add a spec that proves the retry respects it.
5. Retries stop at the cap and the row stays `failed`. No dead-letter table, no alerting on the
   alerting — `GET /events/:id/deliveries` already serves the state to every member of the space.

**DoD:**
- [ ] Migration applied to dev and to the test database
      (`DATABASE_URL="$DATABASE_URL_TEST" npx prisma migrate deploy`).
- [ ] Integration spec: a `failed` row past the delay is retried; a `delivered` one is not; one at
      the attempt cap is not.
- [ ] Unit spec: a retry finds the row `delivered` (acknowledged mid-flight) and does not overwrite it.
- [ ] `DELIVERY_RETRY_ENABLED=false` does nothing.
- [ ] `call`/`whatsapp` rows are never picked up.
- [ ] `npm run openapi:export` re-run if the delivery DTO gained `attempts`.
- [ ] Commit `feat(events): retry failed alert deliveries on a bounded schedule`.

### T09 — Per-camera detection tuning

**Closes:** README Roadmap "per-camera confidence threshold (today one global
`PipelineDefaults.CONFIDENCE_THRESHOLD`)" and "per-camera FPS tuning".

**Problem:** one confidence threshold for every camera, and one cadence ladder for every camera. A
camera pointed at a street and a camera pointed at a hallway need different numbers, and today
tuning one detunes the other.

**Steps:**
1. Migration: nullable `confidenceThreshold Float?` and `minPollSeconds Int?` on `Camera`. Null means
   "use the global default" — so nothing changes for an existing camera and there is no backfill.
2. `PipelineService` reads the camera's value with the global as fallback. `CadenceEngine` clamps its
   ladder's shortest rung to `minPollSeconds` when set.
3. Expose both on the camera DTO and accept them on the camera-update route, validated:
   threshold in `(0, 1]`, `minPollSeconds` at or above the engine's base tick. An out-of-range value
   is `VALIDATION_ERROR`, not a silent clamp.
4. Do **not** add a per-camera cadence *ladder* — the levels stay global. One knob per camera, not a
   configuration language.

**DoD:**
- [ ] Migration applied to dev and test databases.
- [ ] Integration spec: a camera with a null threshold behaves exactly as today.
- [ ] Unit spec: a camera-specific threshold is the one the pipeline compares against.
- [ ] Unit spec: `minPollSeconds` raises that camera's floor and leaves others alone.
- [ ] e2e: `PATCH /cameras/:id` accepts both, refuses out-of-range values.
- [ ] `npm run openapi:export`; `openapi.json` committed.
- [ ] README "Poll cadence" and the API table updated.
- [ ] Commit `feat(cameras): per-camera confidence threshold and poll floor`.

### T10 — DVR capture reliability

**Closes:** README Roadmap "DVR snapshot reliability (retry/backoff/reconnect metrics)";
`http-dvr-client.service.ts:207` `ponytail: one challenge per request`.

**Problem:** a capture that fails records the camera's error and waits for the next tick. That is the
right behaviour for a recorder that is down, and the wrong one for a single dropped TCP connection —
a whole cadence interval lost to a transient. And every ISAPI request pays a fresh digest challenge
round-trip because the nonce is not cached, which doubles the request count against a device that is
already the slowest thing in the loop.

**Steps:**
1. One bounded retry with short backoff inside `HttpDvrClientService.captureSnapshot` for the
   transient classes only (connection reset, timeout). A `401`, a `404` and a `5xx` from the device
   are answers, not transients — do not retry them.
2. Cache the digest nonce per DVR for its server-declared lifetime, falling back to a fresh challenge
   on the first `401` after a cached one. This is the `ponytail:` comment's own upgrade path; remove
   the comment when it lands.
3. Metrics: `dvr_capture_total{cameraId,outcome}` and `dvr_capture_retry_total{cameraId}`. The
   existing `pipeline_poll_*` metrics time the whole poll — these separate the recorder from the
   detector, which is the question "is it the camera or the upstream" that nobody can answer today.
4. Watch the cardinality: these are per-camera labels on a fleet of eight, same as the poll metrics.
   If the fleet ever grows past a few dozen, the labels come off — note the ceiling in a
   `ponytail:` comment.

**DoD:**
- [ ] Unit spec: a connection reset is retried and the second attempt's frame is returned.
- [ ] Unit spec: a `401` is **not** retried.
- [ ] Unit spec: retries are capped and the last failure is the one reported.
- [ ] Unit spec: the nonce is reused across two captures and re-challenged after a `401`.
- [ ] `/metrics` shows both new metrics.
- [ ] The two `ponytail:` comments in `http-dvr-client.service.ts` are re-evaluated: the nonce one
      removed, the XML-parser one kept or removed with a reason in the tracker.
- [ ] Commit `feat(dvr): retry transient captures and reuse the digest challenge`.

## 7. Out of scope

Stated so nobody has to re-derive the reasoning:

- **Redis, Docker, BullMQ, multi-instance.** Declined in plan 02 §1 on cost, reaffirmed for this
  plan. Everything above is single-process by construction. The trigger to revisit is a second host
  or a second tenant, not a preference.
- **Object storage for snapshots.** ADR 001 defers it and isolates the future move to the snapshot
  accessor and the URL mapper. T05's retention is what makes deferring it survivable; it does not
  replace it. Revisit when the `snapshots` table's size becomes a restore-time problem.
- **`call` and `whatsapp` providers.** Their rows stay `pending`, which is the honest state for an
  attempt nobody made. Building them needs a provider contract that does not exist yet, and T08 is
  deliberately written so it never picks those rows up.
- **Webhook authentication on `POST /events/acknowledgements`.** The route is unauthenticated by
  design and the credential in the body *is* the authorization — a provider's `correlationId`, or an
  HMAC token for a mail recipient (`ARCHITECTURE.md`, "Acknowledging without a session"). A shared
  secret per provider is worth adding when a provider exists; it is not a gap today.
- **Per-track events, `PERSON_UPDATED_IN_ZONE`, movement-vs-presence, known-person authorization,
  alert schedules.** These are plan 05 — they need upstream capabilities (`track_id`) this API does
  not receive yet.
- **Poll versus DVR push/WebSocket.** Still undecided, still schema-neutral. T10 improves the poll on
  the assumption it stays; nothing in it forecloses the other transport.
- **`noUncheckedIndexedAccess`, path aliases, the global exception filter, the two logger styles.**
  Real gaps, all in `STANDARDS_GAPS.md`, all churn across the whole tree for no behaviour change.
  They belong to a dedicated cleanup pass, not to a plan that also ships features.
