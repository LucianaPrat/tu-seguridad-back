# 08 — Multi-space Membership, Roles, Permissions and Invitations

> Implementation plan for letting one user belong to many spaces, with a distinct role and
> permission set in each. Audience: an AI coding agent implementing T01–T05 in order. A task is
> complete only when every Definition of Done (DoD) item passes and its result is recorded in
> `08.spaces-roles-invitations.tasks.md`. Frontend counterpart:
> `tu-seguridad-front/plans/spaces-roles-invitations.md`.

## 1. Context and fixed decisions

Today one user = one space = one role (`admin | member`). Enforced by
`SpaceMember.userId @unique`, `Space.ownerUserId @unique`, `spaceId`+`role` claims in the JWT
(`src/cross/common/jwt-payload.type.ts`), and the public `POST /invitations/accept` that auto-creates
a user with a placeholder password and 409s if the email already belongs to any space. Plan 03 §1
rule "a user belongs to exactly one space" is **superseded** by this plan.

Decisions made with the product owner:

- A user can belong to N spaces; role and permissions are per membership.
- Registering from an invitation link does **not** create a personal space.
- Any user can create extra spaces at any time and becomes their admin.
- Invitation acceptance is explicit (accept / decline while logged in), Trello-style.
- Admin edits members' role, visible menu items and (for guests) visible cameras.

## 2. Roles and permissions

`SpaceMemberRole = admin | collaborator | guest`.

| Action | admin | collaborator | guest |
|---|---|---|---|
| See menu items | all, always | per `menuAccess` | per `menuAccess` |
| See cameras | all | all | only `cameraIds` |
| Edit DVR, cameras, zones | yes | yes | no |
| Edit alert routings | yes | yes | no |
| Acknowledge events | yes | yes | no |
| Invite, revoke, change role/permissions, remove members | yes | no | no |
| Rename / delete space | yes | no | no |

Rule: **may edit = role allows it AND member can view that menu item.**

`MenuKey = home | monitor | events | dvr | channels | members` (`profile`, `help` are always
visible and are not permissions). Single source: `src/cross/common/permissions.ts` exporting
`MENU_KEYS`, `DEFAULT_MENU_ACCESS: Record<SpaceMemberRole, MenuKey[]>`:

- admin: all (stored but ignored).
- collaborator: `home, monitor, events, dvr, channels`.
- guest: `home, monitor`; `cameraIds = []` until assigned.

Guest with `events` sees only events of their cameras. Guest `receiveAlerts` defaults to `false`;
when enabled, only alerts of their cameras are delivered.

Invariants: the last admin of a space cannot be demoted or removed (409 `LAST_ADMIN`); an admin
cannot change their own role (409 `SELF_ROLE_CHANGE`).

## 3. Target model (migration `spaces_multi_membership`)

- `SpaceMember`: drop `userId @unique`; keep `@@unique([spaceId, userId])`; add `@@index([userId])`;
  add `menuAccess Json`, `cameraIds Json` (default `[]`).
- `Space`: rename `ownerUserId` → `createdByUserId`, drop `@unique` (informational only).
- `User`: `membership` → `memberships SpaceMember[]`; `ownedSpace` → `createdSpaces Space[]`;
  add `lastSpaceId String?`.
- Enum: `member` → `collaborator`, add `guest`. Data migration: `member` rows become
  `collaborator` with collaborator default menu; admin rows get the full menu.
- `Invitation`: add `role SpaceMemberRole @default(collaborator)`, `menuAccess Json?`,
  `cameraIds Json?`, `declinedAt DateTime?`, `revokedAt DateTime?`. `createdUserId` stays nullable,
  no longer written.
- `Dvr.spaceId @unique` unchanged.

## 4. Cross-cutting rules

- Tenant still comes from the JWT `spaceId` claim only. No tenant header.
- Role and permissions are **never** in the token: they are loaded per request so changes and
  removals apply immediately.
- Every new or changed route has an e2e test in `test/`.
- Errors use existing exception filter codes; new codes: `NOT_A_MEMBER`, `NO_ACTIVE_SPACE`,
  `LAST_ADMIN`, `SELF_ROLE_CHANGE`, `INVITATION_EMAIL_MISMATCH`, `INVITATION_NOT_PENDING`,
  `CAMERA_FORBIDDEN`.

## 5. Tasks

### T01 — Schema and data migration

**Goal:** the database allows N memberships per user and stores roles, permissions and
invitation metadata.

**Steps:**

1. Add `src/cross/common/permissions.ts` (§2).
2. Edit `prisma/schema.prisma` per §3. Generate migration; hand-edit SQL for the enum value rename
   (`member` → `collaborator`) and the `menuAccess` backfill.
3. Fix compile errors from renamed relations (`membership`, `ownedSpace`, `ownerUserId`) in
   accessors (`space.accessor.ts`, `space-member.accessor.ts`) without behaviour changes yet;
   `findByUserId` becomes `findManyByUserId` + `findBySpaceAndUser(spaceId, userId)`.

**DoD:**

- [ ] `pnpm prisma migrate dev` applies cleanly on a copy of the local DB with existing data.
- [ ] Existing members appear as `collaborator` with default menu; admins unchanged.
- [ ] `pnpm build` and `pnpm test` pass.

### T02 — Per-request membership guard and token without role

**Goal:** role/permissions resolved from DB each request; login works with zero spaces.

**Steps:**

1. `JwtPayload` → `{ sub, email, spaceId: string | null, profileCompleted }`. `verifyAccessToken`
   stops requiring `role`; `spaceId` may be null.
2. New global `SpaceMemberGuard` after `JwtAuthGuard` (`auth.module.ts:65-67`): skips `@Public()`;
   if route has `@AllowNoSpace()` and `spaceId` is null, passes; otherwise loads
   `findBySpaceAndUser` → 403 `NOT_A_MEMBER` / `NO_ACTIVE_SPACE`; sets
   `request.member = { spaceId, role, menuAccess, cameraIds, receiveAlerts }`.
3. `RolesGuard` reads `request.member.role`. Add `@RequireMenu(key)` checked in the same guard
   (admin always passes). Add `@CurrentMember()` and `@AllowNoSpace()` decorators.
4. `session.service`: `loadActiveMembership(userId)` picks `lastSpaceId` if still a member, else
   most recent `joinedAt`, else `null`. `issue`/`rotate` no longer read role. Login no longer
   401s on missing membership.

**DoD:**

- [ ] Changing a member's role in DB is honoured on the next request without re-login (e2e).
- [ ] Deleting a membership makes the next request 403 `NOT_A_MEMBER` (e2e).
- [ ] User with no memberships can log in and call `GET /auth/me` (e2e).
- [ ] Existing e2e suite green.

### T03 — Spaces module, switch, `/auth/me`

**Goal:** list, create, switch, rename, delete spaces.

**Steps:**

1. `modules/spaces`: `GET /spaces` (`@AllowNoSpace`) → `[{id, name, role}]`; `POST /spaces {name}`
   (`@AllowNoSpace`) → space + admin membership + default alert routings (split
   `spaceAccessor.createWithOwner` into `createSpaceForUser(userId, name)` reused by register),
   sets `lastSpaceId`, returns new session; `PATCH /spaces/current {name}` (admin);
   `DELETE /spaces/current` (admin) → 409 if the space has a DVR, else deletes space, memberships,
   invitations, routings.
2. `POST /auth/switch-space {spaceId}` (`@AllowNoSpace`): verify membership, write `lastSpaceId`,
   rotate refresh cookie, return `{accessToken}`.
3. `GET /auth/me` returns `spaces[]`, `currentSpace {id, name, role, menuAccess, cameraIds} | null`,
   `pendingInvitationsCount`; drops top-level `spaceId/spaceName/role`.

**DoD:**

- [ ] e2e: create second space, switch, `/auth/me.currentSpace` changes, `/cameras` scoped to it.
- [ ] e2e: switch to a space the user is not in → 403.
- [ ] e2e: non-admin `PATCH /spaces/current` → 403; delete with DVR → 409.

### T04 — Invitation rework and email

**Goal:** invite by email with role/permissions; explicit accept/decline by an authenticated user.

**Steps:**

1. `POST /invitations {email, role, menuAccess?, cameraIds?}` (admin). 409 only when already a
   member **of this space** or pending invite **here** (remove the any-space check,
   `invitations.service.ts:180-189`). Defaults from `DEFAULT_MENU_ACCESS`.
2. `GET /invitations` (admin) pending for current space, now including `role`.
3. `DELETE /invitations/:id` (admin) sets `revokedAt`. `POST /invitations/:id/resend` (admin) new
   token, new expiry, re-send.
4. `GET /invitations/preview?token=` (public, throttled) → `{id, spaceName, invitedByName, email,
   role, expiresAt, userExists}`; 404 when not pending.
5. `GET /invitations/mine` (`@AllowNoSpace`) pending for the caller's email.
6. `POST /invitations/:id/accept`, `POST /invitations/:id/decline` (`@AllowNoSpace`): caller email
   must equal invitation email (`INVITATION_EMAIL_MISMATCH`), invitation pending and unexpired.
   Accept creates membership with invitation role/menu/cameras, sets `lastSpaceId`, returns new
   session in that space.
7. `POST /auth/register` accepts optional `inviteToken`: invitation must be pending and email must
   match; creates the user **without** a space; invitation stays pending (front accepts next).
8. Delete public `POST /invitations/accept`, `acceptWithNewUser`, `acceptWithExistingUser`.
9. Email: extend `CredentialDeliveryPort.deliver` with `{ spaceName, inviterName, role }`.
   `smtp-credential-delivery.service.ts` invitation mail in **Spanish** (product UI language):
   subject `"{inviterName} te invitó a {spaceName} en Tu Seguridad"`, inline HTML + text: inviter,
   space, role label (Administrador / Colaborador / Invitado), button "Ver invitación" →
   `${APP_BASE_URL}/invitations/accept?token=…`, expiry date (`CredentialTtl.INVITATION_DAYS`).
   Logged delivery keeps printing the link in development.

**DoD:**

- [ ] e2e: invite existing user who has another space → 201 (was 409).
- [ ] e2e: register with `inviteToken` → user has 0 spaces; accept → 1 space with invited role.
- [ ] e2e: accept with a different logged-in email → 403 `INVITATION_EMAIL_MISMATCH`.
- [ ] e2e: decline, revoke and expired invitations cannot be accepted.
- [ ] Mail visible in mailpit (`MAIL_ENABLED=true`, `http://localhost:8025`) with working link.

### T05 — Member management and role scoping in existing modules

**Goal:** admin manages members; every module enforces role, menu and guest camera scope.

**Steps:**

1. `GET /members` adds `role`, `menuAccess`, `cameraIds` (permissions only when caller is admin).
   `PATCH /members/:userId {role?, menuAccess?, cameraIds?, receiveAlerts?}` (admin) validates
   `MenuKey`s and that `cameraIds` belong to this space's DVR; applies §2 invariants.
   `DELETE /members/:userId` (admin) removes membership, clears that user's `lastSpaceId` if it
   pointed here.
2. Accessors take an optional `cameraIds` filter; controllers pass it when `member.role === guest`.
3. Apply per module:
   - cameras: list/get filtered; update/delete `@Roles(admin, collaborator)` + `@RequireMenu('dvr')`.
   - zones, dvr (configure / rediscover / link-events): `@Roles(admin, collaborator)` +
     `@RequireMenu('dvr')`.
   - snapshots, streaming (MediaMTX auth hook in `live-stream.service.ts`): guest camera check →
     403 `CAMERA_FORBIDDEN`.
   - events: `@RequireMenu('events')`; guest filtered by camera; acknowledgement
     `@Roles(admin, collaborator)`. Socket.io gateway: guest receives only events of its cameras.
   - alert-routings: `@RequireMenu('channels')`; replace `@Roles(admin, collaborator)`.
   - members, invitations: GET `@RequireMenu('members')`; mutations `@Roles(admin)`.
   - `findActiveRecipients(spaceId)` (`space-member.accessor.ts:61`) takes the event camera and
     excludes guests without it.
   - pipeline polling: unchanged.

**DoD:**

- [ ] e2e guest: `GET /cameras` returns only assigned; `/cameras/:other/live` and snapshots 403;
      `PUT /dvr` 403; `/events` 403 until `events` granted, then only own cameras.
- [ ] e2e collaborator: can edit zones and routings; `POST /invitations` 403.
- [ ] e2e: removing `events` from a member's menu → next `/events` 403 without re-login.
- [ ] e2e: demote/remove last admin → 409 `LAST_ADMIN`.
- [ ] Alert email test: guest without the camera receives nothing.

## 8. Addendum — user language (T06)

Requested after T03. UI can be Spanish or English; email language follows the user.

### T06 — Locale on users and invitations, bilingual mail

**Goal:** every email goes out in the recipient's language.

**Steps:**

1. Prisma: `enum Locale { es en }`; `User.locale Locale @default(es)`; `Invitation.locale Locale @default(es)`. Migration (no data change beyond defaults).
2. `POST /auth/register` accepts optional `locale` (frontend sends browser language mapped to es/en); stored on the user. Invited registration uses the same field.
3. `PATCH /auth/me {locale}` (`@AllowNoSpace`) — profile language selector. Only `locale` for now (profile editing otherwise out of scope). `/auth/me` returns `locale`.
4. `POST /invitations` accepts `locale` (frontend defaults it to the inviter's locale, user can change it); stored on invitation; resend reuses it.
5. Mail rendering keyed by locale: invitation uses `invitation.locale`; magic link and password reset use `user.locale`; alert emails (`alert-email.service.ts`) use each recipient's `user.locale`. One small `{ es, en }` copy table per mail, no template engine.

**DoD:**

- [ ] e2e: register with `locale: 'en'` → `/auth/me.locale = 'en'`; `PATCH /auth/me` changes it; invalid value 400.
- [ ] Unit: each mail renders es and en (subject + link present); invitation mail follows invitation locale, not inviter's.
- [ ] e2e: invitation created with `locale: 'en'` is delivered with English subject (delivery test double).
