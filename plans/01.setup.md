> Implementation plan for the initial setup of the `tu-seguridad-back` NestJS backend.
> Audience: an AI coding agent (or developer) implementing tasks T01–T25 in order.
> Each task has a **Definition of Done (DoD)**: exact commands and observable results. A task is complete only when every DoD item passes.

## 1. Context

This backend belongs to the "person detection in restricted zones" system (see `../README_proyecto_deteccion_personas_AWS.md` in the parent workspace for the original architecture document — note the deviations below):

- 8 home cameras behind a DVR/NVR.
- **This backend owns**: camera/zone configuration (MySQL), the detection pipeline orchestration, zone evaluation (point-in-polygon + hysteresis), technical events, and live event push to the frontend.
- **Person detection is delegated** to the existing external **face-auth API** (`https://api.face-auth.me`): this backend sends camera snapshots and receives person detections with bounding boxes and a precomputed anchor (foot point).
- **Pipeline (v1)**: internal scheduler polls each camera's DVR snapshot URL → sends the image to face-auth persons detect → filters by confidence → evaluates anchors against the camera's zone polygons → occupancy state machine with hysteresis → persists `ZoneEvent`s → broadcasts them over WebSocket.
- Clients: a **React frontend** (separate repo) over HTTP + WebSocket. There is NO external processor pushing data in.
- **MySQL runs locally already** — full Prisma integration from day one (migrations, seed, repositories).
- Production runs under **PM2** on EC2.

Deviations from the original architecture README: no Python video processor (replaced by face-auth API + snapshot polling), person tracking (`track_id`) not available in v1 (events are zone-occupancy transitions, not per-track), backend is Node-only.

Reference project: `/home/daniel/code/face-api` (NestJS 10) — the same codebase behind api.face-auth.me. We import its proven patterns (Either error handling, layered architecture with accessors, 3-level testing, debug/PM2 recipes, hit metering, withSpan tracing) and fix its known gaps (no helmet, no health checks, no env validation, no structured logging, no git hooks).

## 3. Architecture & conventions (apply to every task)

Directory layout (face-api layering, adapted):

```
tu-seguridad-back/
├── src/
│   ├── main.ts                  # bootstrap (see T03)
│   ├── app.module.ts
│   ├── cross/                   # transversal infra, NO business logic
│   │   ├── common/constants.ts  # EnvNames, ErrorCode, defaults
│   │   ├── errors/either.ts     # Either<T> + builders
│   │   ├── interceptors/        # either, hit
│   │   ├── guards/              # jwt auth
│   │   └── decorators/          # @Public(), @CurrentUser()
│   ├── data/
│   │   ├── prisma/prisma.service.ts
│   │   └── accessors/           # one accessor service per aggregate (wraps PrismaService)
│   ├── modules/                 # features: auth, cameras, zones, events, face-auth-client, pipeline
│   └── observability/           # tracing.ts, tracing.helpers.ts (withSpan)
├── prisma/                      # schema.prisma, migrations/, seed.ts
├── test/                        # e2e helpers + *.e2e-spec.ts
├── plans/
├── .vscode/launch.json
├── ecosystem.config.js
└── .github/workflows/pr-tests.yml
```

Rules:
- Dependency direction: `modules → data (accessors) → Prisma`; `cross` usable everywhere. Feature modules NEVER inject `PrismaService` directly — always through an accessor (face-api pattern).
- All env access via `ConfigService.get(EnvNames.X)` — never `process.env` outside bootstrap.
- Services return `Either<T>`; controllers return the Either; the global `EitherInterceptor` unwraps it. No `try/catch` in controllers, no ExceptionFilters.
- All code, comments, docs, commits in **English**.
- One Conventional Commit per task (`feat:`, `chore:`, `test:`, `docs:`, `ci:`) at task completion.
- Every DTO gets `@ApiProperty` and class-validator decorators.
- Never log or expose `snapshotUrl` values (they may embed DVR credentials) — pino redaction + DTO exclusion on responses. v1 rule: return it only on the single-camera GET, never in lists or logs.

Error envelope produced by the interceptor on failure:

```json
{ "statusCode": 404, "code": "NOT_FOUND", "message": "Camera camera_09 not found" }
```

`ErrorCode` enum (extend as needed): `VALIDATION_ERROR(400)`, `INVALID_POLYGON(400)`, `UNAUTHORIZED(401)`, `FORBIDDEN(403)`, `NOT_FOUND(404)`, `CONFLICT(409)`, `UPSTREAM_ERROR(502)`, `UPSTREAM_TIMEOUT(504)`, `INTERNAL_ERROR(500)`.

## 4. Domain model

- **User**: `id`, `email` (unique), `passwordHash`, `role` (`admin` only for now), timestamps.
- **Camera**: `id` (slug `camera_01`…), `name`, `enabled`, `snapshotUrl` (DVR HTTP snapshot endpoint, may embed basic-auth — sensitive), `pollingIntervalSeconds` (default 5, min 1), `confidenceThreshold` (default 0.45, min detScore accepted), timestamps.
- **Zone**: `id` (slug `zone_…`), `cameraId` (FK, delete Restrict), `name`, `enabled`, `polygon` (Json: `[{x,y},…]` normalized `[0,1]`), `geometryVersion` (int, bumps on polygon change), timestamps.
- **ZoneEvent**: `id` (autoincrement), `eventId` (uuid, unique), `eventType` ∈ `PERSON_ENTERED_ZONE | PERSON_EXITED_ZONE`, `cameraId`, `zoneId`, `occurredAt`, `confidence` (max detScore of the triggering poll, null on EXITED), `personsInZone` (int), `anchor` (Json `{x,y}`, null on EXITED). Indexes: `[cameraId, occurredAt]`, `[zoneId, occurredAt]`.
- **Hit**: request metering — `id`, `method`, `route`, `statusCode`, `durationMs`, `userId?`, `isError`, `createdAt`.

Occupancy semantics (v1, no tracking): a zone fires `PERSON_ENTERED_ZONE` when it transitions empty→occupied confirmed by `ENTER_CONSECUTIVE_POLLS` consecutive polls with ≥1 anchor inside; `PERSON_EXITED_ZONE` when occupied→empty confirmed by `EXIT_CONSECUTIVE_POLLS` consecutive polls with 0 anchors inside (hysteresis per architecture README §10.2). Per-track events arrive in a future plan if face-auth exposes track ids.

## 5. External contract — face-auth persons detect

Verified against the face-api source (`src/modules/api/persons/`):

- `POST {FACE_AUTH_API_URL}/api/v1/persons` (prod: `https://api.face-auth.me/api/v1/persons`, Swagger: `https://api.face-auth.me/docs`)
- Headers: `Fa-Domain: {FACE_AUTH_DOMAIN}`, `Fa-Token: {FACE_AUTH_TOKEN}`
- Body: `multipart/form-data`, field `file` = image (jpeg/png)
- 200 response:

```json
{
  "personsDetected": true,
  "imageWidth": 1280, "imageHeight": 720,
  "persons": [{
    "detScore": 0.91,
    "bbox":     { "topLeft": {"x":417,"y":163}, "bottomRight": {"x":596,"y":682} },
    "bboxNorm": { "topLeft": {"x":0.32,"y":0.22}, "bottomRight": {"x":0.46,"y":0.94} },
    "anchor":   { "x": 0.396, "y": 0.947 }
  }]
}
```

- `anchor` is already the normalized foot point (bbox bottom-center) — use it directly for point-in-polygon.
- Errors follow the face-api envelope (`{statusCode, code, message}`); the endpoint is IP-throttled — respect it: never poll faster than configured, map upstream 429/5xx to `UPSTREAM_ERROR` and count them in camera status.

## 7. API surface v1

All routes prefixed `/api/v1` (global prefix `/api` + URI versioning `v1`), except `/docs` and `/health/*`. Everything requires JWT except login, refresh, health and docs.

| Method & path | Notes |
|---|---|
| `POST /api/v1/auth/login` | public; email+password → `{accessToken, refreshToken}` |
| `POST /api/v1/auth/refresh` | public (refresh token in body); rotates pair |
| `GET /api/v1/cameras` | list (snapshotUrl masked) |
| `POST /api/v1/cameras` | create |
| `GET /api/v1/cameras/:id` | detail (includes snapshotUrl) |
| `PUT /api/v1/cameras/:id` | update |
| `DELETE /api/v1/cameras/:id` | 409 CONFLICT if zones exist |
| `GET /api/v1/cameras/:id/status` | pipeline status: lastPolledAt, lastSuccessAt, lastErrorAt, lastErrorCode, lastLatencyMs, lastPersonsDetected, occupancy per zone |
| `POST /api/v1/cameras/:id/analyze` | multipart `file` (image): runs the full pipeline synchronously on the uploaded image (detect → zones → events) and returns the evaluation `{persons, zoneResults, eventsEmitted}` — the manual-test path when the DVR is unreachable |
| `GET /api/v1/cameras/:id/zones` / `POST …/zones` | zone list / create |
| `GET/PUT/DELETE /api/v1/zones/:id` | PUT bumps `geometryVersion` on polygon change |
| `POST /api/v1/zones/:id/validate` | dry-run polygon validation → `{valid, violations[]}` (200 even when invalid) |
| `GET /api/v1/events` | filters: `cameraId, zoneId, eventType, from, to, limit` (default 100, max 1000), newest first |
| `GET /health/live`, `GET /health/ready` | public; ready = terminus + Prisma ping |
| WS namespace `/events` | JWT in handshake `auth.token`; server emits `zone-event` (ZoneEvent payload) on every persisted event |

### T16 — Detection pipeline (snapshot polling + orchestration + analyze endpoint)

**Goal:** the end-to-end loop: snapshot → detect → occupancy → events → WS; plus the synchronous manual path.

**Steps:**
1. `npm i @nestjs/schedule`.
2. `SnapshotService.fetch(camera): Promise<Either<Buffer>>` — GET `camera.snapshotUrl` via axios, timeout `SNAPSHOT_TIMEOUT_MS`, accept image content-types; errors → `UPSTREAM_ERROR`/`UPSTREAM_TIMEOUT`. Never log the URL.
3. `PipelineService.processImage(camera, image): Either<AnalysisResult>` — calls `FaceAuthClientService.detectPersons`, filters `detScore >= camera.confidenceThreshold`, loads enabled zones, runs `OccupancyEngine.evaluate`, persists+broadcasts each transition via `EventsService.emit`, updates `CameraStatusRegistry` (lastPolledAt/lastSuccessAt/lastErrorCode/lastLatencyMs/lastPersonsDetected/zone occupancy snapshot). Returns `{persons, zoneResults, eventsEmitted}`.
4. `PollingScheduler`: on boot (only if `POLLING_ENABLED=true`) registers a dynamic interval per enabled camera (`pollingIntervalSeconds` via `SchedulerRegistry`); each tick: skip if previous tick for that camera still in flight (latest-frame-wins analog — count skips in status); fetch snapshot → `processImage`. Camera CRUD changes re-register intervals (refresh interval registry every 30s — the simpler option). Errors are logged + recorded in status, never crash the scheduler.
5. `POST /api/v1/cameras/:id/analyze` (JWT, multipart `file`, max 10MB via `ParseFilePipeBuilder`): runs `processImage` synchronously with the uploaded image and returns the `AnalysisResult`.
6. `GET /api/v1/cameras/:id/status` now serves the real `CameraStatusRegistry` entry.
7. Tests: pipeline unit test with mocked snapshot/face-auth/accessors — full flow emits ENTERED after N polls and EXITED after M; in-flight skip test; analyze e2e (mock face-auth client binding) asserting `{persons, zoneResults, eventsEmitted}` and that a WS client receives the event.

**DoD:**

- [ ] With `POLLING_ENABLED=false`: boot logs "polling disabled", no timers registered.
