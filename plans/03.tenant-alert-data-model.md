# 03 — Tenant Alert Data Model

> Implementation plan for replacing the setup-era single-admin camera/zone schema with the
> tenant-aware security model required by the frontend.  Audience: an AI coding agent (or
> developer) implementing T01–T08 in order.  A task is complete only when every Definition of
> Done (DoD) item passes and its result is recorded in `03.tenant-alert-data-model.tasks.md`.

## 1. Context and fixed decisions

`DATA_MODEL_REQUIREMENTS.md` is the UI-derived input; this plan owns the backend schema and
migration strategy.  It supersedes the setup-era `User`, `Camera`, `Zone`, and `ZoneEvent`
models for the product domain.  `Hit` remains a technical-metering table.

The following decisions are already made:

- A `Space` is the tenant root.  A space has many users; a user belongs to exactly one space.
  The relationship is represented by `SpaceMember` so role and alert preference stay scoped to
  the membership.  `SpaceMember.userId` is unique as well as `(spaceId, userId)`.
- A space has exactly one current DVR (`Dvr.spaceId` is unique).  DVR rediscovery keeps a camera
  configuration only when its `externalId` still exists.  A missing discovered channel becomes
  `isConfigured = false`; it is not deleted.
- Existing data need not be preserved: production has no data.  The migration may remove the
  old camera/zone/event tables rather than invent a lossy conversion from polygons to rectangles.
- Camera and monitor-zone deletion is logical.  Normal reads exclude `deletedAt IS NOT NULL`.
  Historical alert events remain readable and retain label/type snapshots.
- Zone geometry is a percentage rectangle, not the previous polygon.  Every zone has its own
  alert level (`intruder` or `suspicious`).
- API enum values and database enums are English.  The frontend owns Spanish or other localized
  labels.
- Snapshot image bytes live in MySQL for now.  They are not URLs stored in the database: the API
  produces a tenant-authorized `latestSnapshotUrl` from a snapshot id.  Streaming is explicitly
  out of scope.
- Face Auth identity is one-to-many per user, allowing replacement and historical revocation.
  The provider token is hashed before storage.
- Outbound alert deliveries carry a generated opaque correlation id.  The provider's inbound
  webhook returns that id; the backend resolves it to the delivery and acknowledges the event.

This is a deliberately breaking API and schema change.  It is safe only because there is no
production data and the frontend contract is being introduced together with it.

## 2. Scope and boundaries

In scope:

- Prisma models, MySQL constraints/indexes, migration, seed and test-db migration.
- Accessor boundaries required to enforce tenant scoping and logical deletion.
- The minimum services/DTOs/routes needed to make the persisted model usable by the existing
  auth, camera, zone, events, pipeline, and WebSocket code.
- Snapshot persistence/read authorization, token persistence, invitation membership, routing and
  delivery acknowledgement persistence.

Out of scope:

- A concrete email, WhatsApp, or call provider; use an interface and persist provider ids only.
- Live-stream transport and storage outside MySQL.
- Event retention duration/partitioning, notification retries/backoff, and event cooldown/dedup
  policy.  The schema must not prevent adding them later.
- A polling-versus-WebSocket winner.  Persist camera discovery and status so either ingestion path
  can update the same records; add an adapter boundary rather than two competing schedulers.

## 3. Target relational model

All public ids introduced in this plan are UUID strings generated by Prisma/application code.  The
existing integer `User.id` and `Hit.id` may remain integers to minimize non-domain churn; new
foreign keys to users therefore use `Int`.  Database table names use plural snake_case names.

| Model / table | Key fields | Relations and invariants |
| --- | --- | --- |
| `User` / `users` | `id`, normalized-lowercase `email`, `passwordHash`, `firstName`, `lastName`, `phone`, `avatarUrl?`, `isActive`, `lastLoginAt?`, `profileCompleted`, timestamps | Email globally unique. A user has zero/one `SpaceMember`, many auth tokens, face identities, invitations sent, and acknowledged events. User accounts are deactivated rather than physically removed. Passwords use Argon2id (or the existing bcrypt implementation until an intentional password-hash migration is made). |
| `Space` / `spaces` | UUID `id`, `name`, `ownerUserId`, timestamps | One owner and one-to-many members, invitations, DVR, routing rows, and alert events. Service transaction creates the owner membership with `admin`; DB cannot express that cross-table rule alone. |
| `SpaceMember` / `space_members` | `spaceId`, `userId`, `role`, `receiveAlerts`, `invitedByUserId?`, `joinedAt` | FK to space and user; `@@unique([spaceId, userId])`, `@@unique([userId])`, index `spaceId`. `role` is `admin | member`. This enforces one-space-per-user while retaining membership-scoped state. |
| `Invitation` / `invitations` | UUID `id`, `spaceId`, normalized `email`, `tokenHash`, `invitedByUserId`, `expiresAt`, `acceptedAt?`, `createdUserId?` | Unique `tokenHash`; index `(spaceId, email)` for pending lookup. Do not add a plain unique `(spaceId,email)`: it would prevent later invitations after expiry/acceptance. Service permits only one usable pending invitation per space/email. |
| `AuthToken` / `auth_tokens` | UUID `id`, `userId`, `purpose`, `tokenHash`, `expiresAt`, `usedAt?`, `revokedAt?`, `rotatedFromId?`, `userAgent?`, `ip?` | `purpose` is `refresh | magic_link | password_reset`; unique token hash; self-FK for refresh rotation; indexes `(userId,purpose)` and `expiresAt`. Raw values exist only in cookie/email. |
| `UserFaceIdentity` / `user_face_identities` | UUID `id`, `userId`, `tokenHash`, `isActive`, `lastUsedAt?`, `revokedAt?`, timestamps | Unique provider-token hash and index `(userId,isActive)`. Hashing lets login look up a presented token without persisting it. Re-enrollment revokes prior active identity in one transaction. |
| `Dvr` / `dvrs` | UUID `id`, `spaceId`, `url`, `username`, `passwordEncrypted`, `timezone`, `lastTestAt?`, `lastTestOk?`, timestamps | Unique `spaceId`, so one DVR per space. Password is encrypted reversibly at the accessor boundary; no DTO or log exposes it. |
| `Camera` / `cameras` | UUID `id`, `dvrId`, `externalId`, `name`, `location?`, `status`, `isConfigured`, `isEnabled`, `monitorMode`, `alertType?`, `lastSnapshotAt?`, `deletedAt?`, timestamps | Unique `(dvrId,externalId)`, indexes `dvrId` and `deletedAt`. A full-mode camera uses `alertType`; partial mode evaluates `MonitorZone.alertType`. A deleted camera is never selected for polling or normal API reads. |
| `MonitorZone` / `monitor_zones` | UUID `id`, `cameraId`, `x`, `y`, `width`, `height`, `alertType`, `deletedAt?`, timestamps | Coordinates are `DECIMAL(5,2)`. Add DB checks: `x,y >= 0`, `width,height > 0`, and `x+width,y+height <= 100`; service validates the same rules for clear errors. Index `(cameraId,deletedAt)`. |
| `Snapshot` / `snapshots` | UUID `id`, `cameraId`, `data`, `mimeType`, `byteSize`, `sha256`, `capturedAt`, `createdAt` | `data` is MySQL `MEDIUMBLOB`; enforce app-level max size before write. Index `(cameraId,capturedAt)`. It is served only through a space-scoped authenticated endpoint. Camera list/detail mappers expose a derived API URL, never BLOB data or a DVR credential URL. |
| `AlertRouting` / `alert_routings` | `spaceId`, `alertType`, `channel`, `enabled`, timestamps | Unique `(spaceId,alertType,channel)`. Enums: `alertType = intruder | suspicious`, `channel = call | whatsapp | email`. |
| `AlertEvent` / `alert_events` | UUID `id`, `spaceId`, `cameraId?`, `zoneId?`, `cameraLabelSnapshot`, `alertType`, `detectedAt`, `snapshotId?`, `acknowledgedAt?`, `acknowledgedByUserId?` | `cameraId` and `zoneId` use `ON DELETE SET NULL` for a future physical purge; logical delete does not modify history. `snapshotId` uses `SET NULL`. Index `(spaceId,detectedAt DESC)` and `(spaceId,alertType,detectedAt DESC)`. Acknowledging user must belong to the event space; service verifies it. |
| `EventDelivery` / `event_deliveries` | UUID `id`, `eventId`, `channel`, `recipientUserId`, `status`, `correlationId`, `sentAt?`, `deliveredAt?`, `providerMessageId?`, `error?`, `inboundReceivedAt?` | One row per channel/recipient attempt. `correlationId` and non-null `providerMessageId` are unique; index `eventId`. `status = pending | sent | failed | delivered`. A matched inbound reply updates this row and atomically acknowledges its event. |
| `Hit` / `hits` | existing fields | Remains technical telemetry. Keep `userId` nullable; add only a relation/index if a real reporting query needs it. It is not part of the tenant authorization model. |

The old `ZoneEvent` table/model is replaced by `AlertEvent`: occupancy transitions are internal
pipeline state, while UI history is an alert event with a business alert type.  No old data exists
to retain.  The previous polygon `Zone` is replaced by `MonitorZone` rectangles.

### Referential diagram

```text
User ──0..1 SpaceMember──1 Space──1 Dvr──* Camera──* MonitorZone
  │             │                │                   │
  │             └── alert prefs   ├──* Invitation     └── soft delete only
  ├──* AuthToken                  ├──* AlertRouting
  └──* UserFaceIdentity           └──* AlertEvent──* EventDelivery
                                      │       └── optional Snapshot
                                      └── optional Camera / MonitorZone
Camera ──* Snapshot
```

## 4. Cross-cutting rules

- A request derives `spaceId` from the authenticated user membership once, then every accessor
  accepts it and includes it in its query.  No controller/service may authorize an `AlertEvent`,
  `Camera`, `MonitorZone`, or `Snapshot` from a bare resource id.
- Accessors, not modules, are the only layer allowed to inject `PrismaService`.  Add dedicated
  accessors for each aggregate or a small intentional aggregate grouping; never put Prisma calls
  in a controller.
- Soft-delete queries use a common explicit predicate (`deletedAt: null`), including counts,
  polling/discovery, DTO lookup and snapshot authorization.  Restore is not in scope.
- The `Dvr.passwordEncrypted` and any DVR-derived credentials use the existing field-encryption
  pattern with a purpose-specific key/config name.  Snapshot BLOBs, token hashes, face identity
  hashes, `Authorization`, `Fa-Token`, and DVR fields must be covered by Pino/Sentry redaction.
- `lastSnapshotAt` records camera freshness.  The `latestSnapshotUrl` returned to the UI is
  derived from the latest authorized snapshot record; it must not become a second secret-bearing
  `snapshot_url` column.
- The migration SQL adds checks Prisma cannot model.  Test both Prisma validation and raw MySQL
  constraint rejection for rectangle bounds.  Do not rely only on frontend validation.

## 5. Tasks

### T01 — Contract and migration inventory

**Goal:** turn the agreed data model into one reviewed source of truth before changing Prisma.

**Steps:**

1. Update `plans/DATA_MODEL_REQUIREMENTS.md` only where needed to record the resolved decisions:
   one-space membership, logical camera/zone deletion, MySQL snapshot BLOBs, English wire enums,
   face identity table, rediscovery rule, and correlation ids.  Keep UI observations distinct from
   backend decisions.
2. Add a concise decision record under `docs/decisions/` covering MySQL BLOB snapshot storage and
   its consequence: authenticated derived URLs now, object storage can replace only the snapshot
   accessor later.
3. Inventory every old field and route that changes: `Camera.snapshotUrl`, slug ids, polygon
   geometry, `ZoneEvent`, admin-only user role, and stateless refresh JWTs.  Mark each as
   replace/remove/compatibility bridge in this plan's tracker before code starts.
4. Confirm both development and test databases are disposable.  Back up neither production nor
   local data as part of this task; no production data exists, but the implementation task must
   still state its destructive migration explicitly.

**DoD:**

- [ ] Requirements and decision record are English and do not contradict this plan.
- [ ] The inventory identifies all current Prisma models/accessors/routes that need migration.
- [ ] Tracker records database-disposability confirmation and no unresolved schema decision.

### T02 — Prisma schema and destructive migration

**Goal:** create the tables, relations, enums, indexes and database constraints in section 3.

**Steps:**

1. Replace the setup-era Prisma domain models/enums with the target models.  Preserve `Hit`, but
   update its user typing only if necessary for the retained integer user id.
2. Use `@map`/`@@map` for the snake_case database names listed above and `@db.Decimal(5, 2)` for
   monitor-zone coordinates.  Use `@db.MediumBlob` for snapshot bytes.  Keep all relationship
   names explicit where models have multiple references to `User`.
3. Generate the migration with `npx prisma migrate dev --name tenant_alert_data_model`, inspect it,
   and edit its SQL only to add named MySQL check constraints and any required history indexes.
   The migration may drop/recreate `cameras`, `zones`, and
   `zone_events`; it must not leave obsolete foreign keys or columns.
4. Add a migration test/SQL review checklist asserting all FK delete actions, unique constraints,
   indexes, `user_id` uniqueness in memberships, one DVR per space, and rectangle checks.
5. Apply the exact migration to the test database:
   `DATABASE_URL="$DATABASE_URL_TEST" npx prisma migrate deploy`.
6. Regenerate the Prisma client and adapt the seed so it creates one profile-complete active admin
   user, its space, owner membership and routing defaults. Do not seed a DVR: onboarding must
   persist a real encrypted DVR credential through its accessor.

**DoD:**

- [ ] `npx prisma format` and `npm run prisma:generate` pass.
- [ ] `npx prisma migrate deploy` succeeds against development DB.
- [ ] `DATABASE_URL="$DATABASE_URL_TEST" npx prisma migrate deploy` succeeds against test DB.
- [ ] A raw SQL test proves MySQL rejects invalid monitor-zone bounds and duplicate user
  memberships/DVRs.
- [ ] `npm run prisma:seed` is idempotent and leaves no plaintext DVR password or snapshot bytes
  in logs.

### T03 — Tenant-scoped data access and lifecycle rules

**Goal:** make the new schema safe to use before exposing new endpoints.

**Steps:**

1. Replace old camera/zone/event accessors and add accessors for spaces, memberships, DVRs,
   invitations, auth tokens, face identities, snapshots, alert routing, alert events and event
   deliveries.  Register them through `DataModule`.
2. Change public lookup/query methods to require `spaceId` and include it in their Prisma `where`
   path.  For camera/zone/snapshot lookups, scope through `dvr.spaceId` or `camera.dvr.spaceId`.
3. Implement logical delete for cameras and monitor zones.  List, detail, discovery, pipeline and
   count queries must exclude soft-deleted rows; historical alert queries must retain snapshots.
4. Implement DVR discovery reconciliation in one transaction: upsert discovered channels by
   `(dvrId,externalId)`, retain matching monitor config, mark non-discovered active cameras as
   `isConfigured=false`, and never revive a manually deleted camera without an explicit restore
   decision.
5. Store and retrieve DVR credentials only through reversible field encryption.  Store raw auth,
   invitation and face-identity values only as purpose-appropriate hashes.  Add explicit revoke,
   consume, expiry, and refresh-rotation queries.
6. Update `truncate-all.ts` in FK-safe order for every new table, including delivery/event/snapshot
   rows before their parents.

**DoD:**

- [ ] `grep -rn "PrismaService" src/modules/` is empty.
- [ ] Accessor unit/integration tests show a resource in Space A cannot be found, updated,
  deleted, or read through Space B's scope.
- [ ] Tests cover soft deletion, rediscovery retain/missing behavior, token hash lookup and
  revocation, and encrypted DVR-password round trip.
- [ ] `npm run test:int` passes.

### T04 — Authentication, membership and invitation persistence

**Goal:** make login and onboarding reflect the new user/space state.

**Steps:**

1. Extend JWT/access-token payload and `/auth/me` with the current `spaceId`, membership role,
   `profileCompleted`, and active status.  Reject deactivated users and users without an accepted
   membership.
2. Replace stateless refresh acceptance with `AuthToken` verification: hash/lookup the cookie
   token, validate purpose/expiry/revocation, revoke it, create the rotated successor and set the
   new HttpOnly cookie atomically.
3. Add registration, invitation creation/acceptance, profile completion, password reset and magic
   link service flows using generic responses for registered/unregistered email.  Acceptance
   creates/links exactly one user and one membership, marks the invitation used, then issues the
   profile-completion session.
4. Add Face Auth identity registration/login lookup through `UserFaceIdentity`; only active
   identities authenticate.  Re-registration revokes prior active records instead of overwriting
   history.
5. Enforce role authorization at the service/guard boundary: only space admins manage DVR,
   members, routing and destructive configuration; members may use permitted read routes.

**DoD:**

- [ ] Unit tests cover refresh rotation/replay rejection, inactive user rejection, one-space
  enforcement, invitation expiry/one-time use, and profile-completion gate.
- [ ] E2E tests prove a user from another space receives `FORBIDDEN`/`NOT_FOUND` without data
  disclosure.
- [ ] Raw refresh, magic-link, password-reset, invitation and face-provider tokens never appear
  in an HTTP response, log fixture, database assertion, or OpenAPI example.

### T05 — DVR, camera, rectangle-zone and snapshot behavior

**Goal:** replace manual camera/polygon CRUD with DVR-owned cameras and UI-compatible snapshots.

**Steps:**

1. Replace manual camera creation with an admin-only DVR initialize/update flow that validates
   connectivity, persists encrypted DVR configuration, discovers camera channels, and runs the
   reconciliation from T03.  Keep DVR URLs permissive enough for LAN hosts; do not apply an
   internet-only URL validator.
2. Adapt camera endpoints/DTOs to expose discovery-backed fields, monitor configuration,
   status/freshness and a derived `latestSnapshotUrl`.  Accept only operator-editable fields;
   never accept `externalId`, status or a DVR credential from a camera update.
3. Replace polygon DTOs/geometry/occupancy evaluation with percentage-rectangle monitor zones.
   Validate decimal bounds and ensure full-mode alerts use `Camera.alertType` while partial-mode
   alerts use the matching zone level.  Do not process deleted/disabled/unconfigured cameras.
4. Add a snapshot accessor/service that saves a captured image to `Snapshot.data`, records mime,
   size, SHA-256 and timestamp, then serves it from a tenant-scoped authenticated endpoint.
   Replace old camera `snapshotUrl` persistence, pipeline fetch assumptions and secret-bearing DTO
   paths.  Event records reference `Snapshot.id`; DTOs map it to an authorized read URL.
5. Establish a snapshot size limit in validated config and reject oversized images before the
   MySQL write.  Document that retention and external object storage are later operational work.

**DoD:**

- [ ] Camera initialization discovers/upserts channels, preserves matching configuration and
  marks missing channels `isConfigured=false`.
- [ ] Camera and zone deletion return success but remove them from normal list/detail/poll queries;
  an existing event still renders its saved camera label and alert level.
- [ ] Unit and integration tests cover both full and partial alert-level selection, invalid
  rectangle rejection, and snapshot BLOB round trip without exposing bytes in list responses.
- [ ] An authenticated Space A request cannot download a Space B snapshot by id.

### T06 — Alert events, routing, delivery and acknowledgement correlation

**Goal:** persist the UI history and notification domain independently of detection internals.

**Steps:**

1. Replace `ZoneEvent` emission/query DTOs, mappers, accessors and WebSocket payloads with
   `AlertEvent`.  At creation, copy the camera label and selected alert type into immutable event
   fields; attach the saved snapshot when present.
2. Query events only by `spaceId`, with cursor pagination (stable `detectedAt,id` cursor), alert
   type filter and date lower bound.  Do not retain the old unbounded/default-100 list contract.
3. Resolve enabled `AlertRouting` rows and opted-in active space members into one `EventDelivery`
   per event/channel/recipient.  Persist a random correlation id before handing work to a future
   provider adapter.
4. Add a provider-agnostic inbound acknowledgement service that looks up the correlation id,
   deduplicates repeated provider callbacks, records receipt/delivery state, and atomically sets
   `AlertEvent.acknowledgedAt`/`acknowledgedByUserId` when the responder is resolvable.
5. Keep sending itself behind an interface.  No provider credential, webhook signature scheme, or
   retry policy is invented by this data-model plan.

**DoD:**

- [ ] Event list uses its composite tenant/history indexes and never leaks another space's event.
- [ ] An event can have multiple delivery rows across channels and recipients.
- [ ] Duplicate inbound correlation callbacks are idempotent; an unknown correlation id reveals no
  event information.
- [ ] Event, routing, delivery and gateway tests pass, including camera/zone logical-deletion
  history behavior.

## 6. Acceptance checklist

- [ ] Every product-owned row can be reached from exactly one `Space`, directly or through DVR /
  camera / membership, and accessors require that scope.
- [ ] One user has one membership; one space has one DVR; one DVR has unique external camera
  channels.
- [ ] Camera/zone deletes are logical; event history and alert delivery attempts are durable.
- [ ] Rectangle geometry and all enum values match the frontend contract and use English codes.
- [ ] Passwords and all raw bearer/magic/invitation/face tokens are never persisted in plaintext.
- [ ] DVR passwords are reversible-encrypted but never sent to a client or logged.
- [ ] Snapshot bytes are MySQL BLOBs and can only be read through space-scoped authorization.
- [ ] Events support multi-channel, multi-recipient delivery and idempotent inbound correlation.
- [ ] `openapi.json`, README, architecture documentation, seed, test truncation and all test
  fixtures match the final schema.

## 7. Deferred decisions

- Snapshot retention/cleanup schedule and move to object storage.
- Live streaming protocol, authorization and stream URL contract.
- Detection cooldown/dedup policy and its persistence requirements.
- Delivery-provider selection, webhook authentication, retries and delivery state transitions.
- Poll job versus DVR push/WebSocket implementation.  Both must call the same discovery/status
  and snapshot persistence services.
