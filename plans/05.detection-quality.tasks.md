|---|---|---|
| T01 — Count what the detector answers | ✅ Done and committed | `pipeline_persons_detected_total{cameraId,outcome}` registered in `metrics.module.ts`, incremented in `PipelineService.processImage` where the upstream result is unpacked. `outcome` is `persons`, `empty` (upstream reported nobody) or `filtered` (reported somebody this camera's threshold dropped) — the split is a module-level `detectionOutcome` helper, and a poll the detector never answered increments nothing. The debug line was not promoted; instead one info line per poll that actually saw somebody: `camera <id> saw N person(s), M area(s) confirmed`. Bounded by real presence, so it cannot spam an empty scene, and a sighting that confirms nothing — the thing this plan is about — is now visible at `LOG_LEVEL=info`. Four unit tests cover the three outcomes plus the never-answered case. README metrics inventory and `ARCHITECTURE.md` updated. |
| T02 — Commit the bench as a script | ✅ Done and committed | Deviation from the plan: `scripts/try-detect.ts` was extended instead of adding `scripts/detection-bench.ts`. It already booted Nest and called the real `FaceAuthClientService` for one image; a second script would have duplicated that to differ only in the loop. It now takes a file **or** a directory plus an optional gap, prints `file / persons / scores` as TSV and, for a batch, a summary with the hit rate and the `detScore` range. Gap clamps to ≥5 s and defaults to 12 s (§2.5 of the plan). Single-image usage is unchanged and still sleeps not at all. `docs/BEST_PRACTICES.md` gained a "Measuring detection recall" section with the measured baseline to compare against. |
| T03 — K-of-N entry confirmation | ✅ Done and committed | `OccupancyEngine` now keeps `{ inside, window, misses }` per area: entry confirms when `ENTER_HITS_REQUIRED` of the last `ENTER_WINDOW_POLLS` frames put an anchor inside, exit stays a consecutive run of `EXIT_CONSECUTIVE_POLLS` misses. New env pair defaults to `2` / `4` from `PipelineDefaults`; Joi refuses hits above the window through `Joi.ref`, and the constructor throws on the same condition so a direct construction cannot bypass it. `ENTER_CONSECUTIVE_POLLS` is gone from `EnvNames`, the Joi schema, `PipelineDefaults` and the README. `hasPendingOccupancy` now keys on "confirmed occupied, or a sighting still inside the window", so the detection cadence still rises on the raw sighting and falls once the window slides past it. Six new tests: non-consecutive confirm, lone hit never confirms, the window sliding, pending clearing, `hits === window` reproducing the old consecutive rule exactly, and the constructor guard. |
| T04 — A throttle is not an outage | ✅ Done and committed | `ErrorCode.UPSTREAM_THROTTLED` (503 outbound — nothing the caller did was rate limited) plus three changes in `FaceAuthClientService`: opossum `errorFilter` excludes a `429` from the breaker, `mapError` parks detection until `Retry-After` (or 5 s, the usual case since the upstream sends no header), and `detectPersons` short-circuits while the park stands without spending an HTTP request. Four tests: the mapping, the park short-circuiting the next call, `Retry-After` honoured then released on the fake clock, and ten real `429`s leaving `circuitState === 'closed'` while ten `500`s still open it (that last one was already covered). `openapi.json` regenerated — the new code is the only diff. |
| T05 — Stop the zones from lying | ⚠️ Needs a manual/owner step | Not code. Cameras 03, 04 and 05 are `monitorMode = full` while carrying 1, 1 and 2 non-deleted `monitor_zones` rows, which `resolveZones` ignores. Owner picks per camera: switch to `partial` (alerts then depend on the drawn area — re-check `GET /cameras/:id/status` afterwards) or delete the zones through the API. |
| T06 — Keep the raw evidence frame, off by default | ✅ Done and committed | `SNAPSHOT_KEEP_RAW` (Joi boolean, default `false`). `storeEvidence` stores the untouched capture as a second row when the flag is on **and** annotation actually produced different bytes — a frame the annotator could not decode is already the captured bytes, so a copy would be a duplicate for nothing. The event still points at the annotated row; a failed raw copy is logged and dropped. The `ponytail:` note in `annotate-frame.ts` is gone — it asked for exactly this feature ("store both when someone needs the untouched pixels"), so it was replaced with a line naming the flag and why the annotated re-encode is not evidence for a recall audit. Three tests: one row by default, two with the flag on and the last call carrying the captured object, and a failed copy not costing the alert. |

## Owner steps this plan surfaces

1. **`.env` on the API host.** `ENTER_CONSECUTIVE_POLLS` is no longer read; the replacements have
   Joi defaults, so the app boots without them and behaves as `2` of `4`. To pin them explicitly:

   ```
   ENTER_HITS_REQUIRED=2
   ENTER_WINDOW_POLLS=4
   ```

   `SNAPSHOT_KEEP_RAW=true` only while the upstream's recall is under audit.

2. **Restart the API** to pick any of this up — the running process still holds the old occupancy
   engine, and its in-memory occupancy, cadence and cooldown state resets on restart either way.

3. **T05**, above.

4. **The optics, lighting and provider steps** in `plans/05.detection-quality.md` §6, none of which
   code can do. The message for the provider is written:
   [`docs/face-auth-detection-findings.md`](../docs/face-auth-detection-findings.md).

## What was deliberately not touched

- `plans/01.setup.md` still describes `ENTER_CONSECUTIVE_POLLS` and the four-state occupancy
  machine. It is the record of what plan 01 built, not live documentation, and rewriting a shipped
  plan to match a later one destroys the history that makes the tracker worth reading. The plan's
  own DoD asked for no surviving reference; this is the stated exception.
- `CONFIDENCE_THRESHOLD` — decision D1. Failures come back as empty arrays, so there is nothing a
  threshold change could admit.
